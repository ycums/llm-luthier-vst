# delegate-subtasks

親セッションから、指定したセッションIDのセッションへ「サブタスクを
消化してほしい」という依頼を送るSkill。対象セッションが同一マシン上
で到達可能な場合は、依頼に先立って専用のgit worktreeを新規作成し、
対象セッションがそこへ切り替えて作業できるようにする。到達できない
場合、worktreeはこのSkillでは構成しない。

## 引数

- 第1引数: 依頼先セッションのセッションID(必須)。
  一覧の確認には `mcp__ccd_session_mgmt__list_sessions` ではなく、
  見つかったツール(確認済みの例: `mcp__Claude_Code_Remote__list_sessions`)
  を使う(理由は下記「注意」参照)。対象セッション側で `/nop` を実行
  して得られたIDでもよい。

引数が渡されていない場合は、ユーザーに対象セッションIDを尋ねる。

## 手順

1. 渡されたセッションIDが自分自身(現在のセッション)のIDと一致しない
   ことを確認する。一致する場合はエラーとしてユーザーに伝える。

2. 対象セッションの情報を取得し、実在すること・アーカイブされていない
   ことを確認する。
   - `mcp__ccd_session_mgmt__get_session` は**存在しない環境がある**
     (2026-09-07時点で2つの独立した環境で確認)。`ToolSearch` で
     `get_session` を探し、見つかったツール(確認済みの例:
     `mcp__Claude_Code_Remote__get_session`)を使う。
   - 確認する項目:
     - セッションが存在し、アーカイブ済みでないこと。存在しない/
       アーカイブ済みの場合はユーザーに報告して中断する。
     - `external_metadata.cross_session_inbound` の値。`"available"`
       であることを確認する(確認済み: 観測した全セッションでこの値
       だった)。それ以外の値を観測した実績はまだなく、その場合の
       挙動は未確認。`"available"` でない値を見つけた場合は、配送
       できない可能性があるとしてユーザーに報告してから続行するか
       判断する。
     - `isRemote` フィールドは**実在しない**(旧版の誤り。確認済み)。
       ローカル/リモートの判定は手順3で行う。

3. 対象セッションが**同一マシン上で到達可能か**を判定する。旧版は
   `isRemote` フィールドで判定していたが、そのフィールドは実在しない
   ため、実際の到達可否を直接調べる方式に置き換える。
   a. `ListAgents` を呼び、対象セッションのID(または名前)が一覧に
      現れるか確認する。
   b. **現れる場合(同一マシン、到達可能)**、専用のworktreeを用意する:
      i. 現在(親セッション)がgitリポジトリ内で作業していることを
         確認する。そうでなければユーザーに報告して中断する。
      ii. `git worktree add <path> -b <branch>` (Bash) で、対象セッ
          ション専用の新しいworktreeを作成する。パス・ブランチ名は
          対象セッションIDやタイトルから一意に識別できるものにする
          (例: `.claude/worktrees/delegate-<session_id短縮形>`)。
          親セッション自身はこのworktreeには切り替えない
          (`EnterWorktree` は親では使わない。切り替わるのは対象
          セッション側)。
      iii. 作成したworktreeの絶対パスを控えておく。
   c. **現れない場合(到達不可、別マシン/リモートの可能性が高い)**、
      手順3全体(worktree作成)をスキップする。
      - `get_session` の `environment_kind`(観測値: `anthropic_cloud`,
        `bridge` など)は補助的な参考情報として使ってよいが、
        到達可否の一次判定は必ず本項(a)(b)のreachabilityチェックで
        行うこと。`environment_kind` の値と到達可否の対応関係は
        完全には確認できていない(未確認)。

4. 依頼メッセージを送る。
   - **手順3で到達可能と判定した場合**: `SendMessage` で対象セッション
     へ送る。内容は、手順3で作成したworktreeの絶対パスを伝え、まず
     `EnterWorktree`(`path: "<そのパス>"`)でそこへ切り替えてから、
     残っているサブタスクを1つずつ消化してほしいこと。
   - **到達不可と判定した場合**: `SendMessage` は失敗する(確認済み:
     `to` にセッションIDを渡すと `No agent named '...' is reachable`
     が返り、`ListAgents` にも現れない)。代わりに次の経路を使う:
     a. `mcp__Claude_Code_Remote__create_trigger` を、`persistent_session_id`
        に対象セッションIDを指定し、`cron_expression` と `run_once_at`
        の**両方を省略**して作成する(poke-only Routine)。
        - このとき「このtriggerはMCPコネクタを保持しないため、発火
          したセッションはコネクタツール無しで動く」という警告が
          返る(確認済み)。persistent-sessionバインドの場合、対象
          セッション自身の既存のツール構成がそのまま使えるかどうかは
          **未検証**(発火自体と、対象セッションが処理を進めることは
          確認できたが、その際にコネクタ系ツールを実際に呼び出せるか
          は未確認のまま残っている)。ツール呼び出しを伴う依頼を送る
          場合は、送信後に対象セッションが実際にツールを呼べているか
          を確認すること。
        - worktreeの案内は行わない(手順3cによりスキップ済み)。
     b. `mcp__Claude_Code_Remote__fire_trigger` で即時発火する。戻り値
        の `session_id` で着信を確認できる(確認済み: 実際に対象
        セッションの `updated_at` とトークン使用量が更新されることを
        確認した)。
     c. `mcp__Claude_Code_Remote__delete_trigger` で一時Routineを削除
        する(残すとユーザーのRoutine一覧が汚れる)。
   - **(共通・必須)** 依頼メッセージには次を必ず含める:
     - サブタスクがなくなるまで繰り返し消化してほしいこと。作業中に
       判断に迷うものがあれば報告に含めてよいこと。
     - **報告先(復路)を明示する。** 委任先が報告先を持たないまま
       進めてしまい、親が状況に気づけない、というスキルの欠陥が
       実際に発生した(このスキル自身の運用で観測)。次のいずれかを
       対象セッションの状況に応じて指定すること:
       - 対象セッションがgitリポジトリで作業している場合: 作業を
         コミット・push(可能ならPR作成)し、**ブランチ名・コミット
         ハッシュ・変更内容の要約を、自分の最後のターンの発言
         (プレーンテキスト)として書き出す**こと。この発言内容は
         `get_session`/`list_sessions` の `post_turn_summary`
         (`status_category` / `status_detail` / `recent_action`)
         として、親セッションがツール呼び出し無しに読み取れる
         (確認済み: 実際に別セッションへ本経路でpokeし、
         `post_turn_summary` に反映されることを確認した)。コネクタ
         の有無に依存しない、最も確実な復路である。
       - 途中で判断に迷い作業を止める場合(質問がある場合)も同様に、
         **黙って止まらず、最後のターンの発言に質問をそのまま書く**
         こと。これが `post_turn_summary.status_category: "need_input"`
         等として親から見えるようになる(下記手順6参照)。

5. 対象セッションのタイトルを、委任したタスク内容が分かる名前に変更
   する(`mcp__Claude_Code_Remote__set_session_title`)。
   - **手順4の送信に成功した後**に行う。送信前に行わないのは、送信が
     失敗した場合にタイトルだけ変わって内容と食い違う状態を避けるため。
   - **タイトルは20文字以内**にする(ツール自体の上限は500文字だが、
     セッション一覧で複数のセッションを見分けられるようにするための
     本スキル独自の運用ルールとして20文字以内とする)。
   - 決め方(優先順位):
     1. ユーザーから具体的なタスク名・キーワードが与えられていれば
        それを使う。
     2. 与えられていなければ、手順4で送る依頼メッセージの主題を
        1フレーズに圧縮する(例:「〇〇の実装知見をフィードバックし
        △△機能を追加する」なら『〇〇知見+△△追加』のように名詞句化
        する)。
     3. 圧縮しても20文字を超える場合は、末尾から機械的に削るのではなく、
        最も具体的な固有名詞・対象を優先して残す。
     4. 同じ親セッションから複数の対象セッションへ別々の依頼を送る
        場合、タイトルだけで区別できるよう、対象ごとに異なる具体語を
        必ず含める(同一文言の使い回しは禁止)。デフォルトの
        `"No operation"` のまま放置しない。
   - **リネームに失敗しても、依頼送信自体は失敗扱いにしない。** 手順4
     の送信が成功していれば依頼は既に届いているため、リネームは
     付随的なブックキーピングと位置づける。失敗した場合は警告として
     ユーザーへの報告(手順7)に含め、処理は続行する。

6. **(必要に応じて)** 依頼が重い/時間のかかる内容で、かつ状況把握の
   手段がpolling以外に無い場合は、`mcp__Claude_Code_Remote__send_later`
   などで一定時間後に自分自身への確認メッセージを予約し、その時点で
   対象セッションに `get_session` を呼んで `post_turn_summary.status_category`
   を確認する。
   - `need_input` など作業停止を示す値であれば、対象セッションの
     最後の発言(質問)を読み、回答が必要ならユーザーに判断を仰ぐか、
     手順4bの trigger経由の方法で回答を送り返す。
   - `completed` であれば、`status_detail` / `recent_action` を要約
     としてユーザーに報告する。
   - 毎回機械的にscheduleする必要はない。軽い委任であれば省略してよい。

7. 送信結果をユーザーに簡潔に報告する。含めるべき項目:
   - 成功したこと、対象セッションの(変更後の)タイトル
   - ローカルの場合は作成したworktreeのパス
   - **どの経路で配送したか**(`SendMessage` / trigger経由のいずれか)
   - リネームの成否(失敗した場合はその旨と、依頼自体は成功している
     ことを明記する)

## 注意

- `SendMessage` は同一マシン上で `ListAgents` に現れるセッションにしか
  届かない。異なる環境(`claude.ai/code` のリモートセッション等)には
  届かない(確認済み: `to` にセッションIDを渡すと
  `No agent named '...' is reachable` が返る)。
- worktreeの新規作成は破壊的操作ではないが、対象リポジトリの状態に
  依存する。作成に失敗した場合はエラー内容をそのままユーザーに伝え、
  メッセージ送信は行わない。
- 本スキルが依拠する `mcp__Claude_Code_Remote__*` 系ツールも、環境に
  よっては別名・別サーバーの可能性がある。ツール名は都度
  `ToolSearch` で確認し、断定的なハードコードはしない。
- 本スキルの記述中「確認済み」とあるものは、2026-09-07時点で少なくとも
  1つの実環境(claude.ai/code 上のセッション)で実際に動作を確認した
  事実である。「未確認」とあるものは、観測はされたが再現・検証は
  していない事項であり、今後の作業でツールの実際の挙動が異なる場合は
  そちらを優先すること。
