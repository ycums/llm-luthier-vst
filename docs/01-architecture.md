# 01. アーキテクチャ

## 全体像：回転速度の違う三重ループ

本システムは単一のパイプラインではなく、**周回コストと収束速度が桁違いに異なる3つのループ**の入れ子として設計する。ループを混同すると、収束しない処理を延々と回すか、逆に必要な改訂を見送ることになる。

| | ループ1：フィット | ループ2：仕様改訂 | ループ3：到達 |
|---|---|---|---|
| いつ回る | 実行時 | 開発時 | 実行時 |
| 単位 | 1音源 | コーパス | 1セッション |
| 目標 | 与えられた音源 | エンジンの表現力 | ユーザーの脳内イメージ |
| 判定者 | 客観指標 | 残差プロファイル | 人間の耳 |
| 1周のコスト | 数百ms | 数日 | 数十秒〜数分 |
| 許容周回数 | 数千 | 数十 | 5〜10 |
| 収束条件 | 指標が閾値内 | 改訂が発生しなくなる | ユーザーが満足する |

## ループ1：フィット（内側・自動）

```
ターゲット音源
   ↓
分析スキル（アナライザ群を実行）
   ↓
パラメータ推定（特徴量 → エンジン仕様空間へ写像）
   ↓
中間プリセット（時系列を持つ構造化データ)
   ↓
VSTエンジン（ヘッドレスでレンダ）
   ↓
残差の客観評価（指標ベクトル）
   ↓
残差の切り分け ──[フィット誤差]──→ パラメータ推定へ戻る
                └─[能力ギャップ]──→ ループ2へエスカレーション
```

### 残差の切り分けが全体の心臓部

「まだ追い込めていないだけ」と「そもそもエンジンに表現する場所がない」を区別できないと、ループ1が永久に回り続ける。

判定は**残差の分布パターン**で行う。スカラー1個に潰してはならない（`docs/04-metrics.md` が指標をベクトルで返す理由がこれ）。

| 残差の偏り | 疑われる不足 |
|---|---|
| アタック直後の短時間区間に集中 | トランジェント／ノイズ層の自由度不足 |
| 定常部の特定帯域に山が残る | フォルマントフィルタバンクの帯域数不足 |
| 時間方向に周期的な誤差 | モジュレーション経路の不足 |
| ピッチ遷移区間だけ悪化 | グライド／ポルタメント表現の不足 |
| 全体に一様で、反復しても下がらない | パラメータ推定の探索が局所解に落ちている（＝ループ1の問題） |

### エスカレーション条件

以下のいずれかを満たしたとき、能力ギャップとしてループ2へ送る。

- N回反復しても特定の指標だけが単調に下がらない（Nは暫定。`docs/06` 参照）
- 残差が上表のいずれかのパターンに明確に偏っている
- 異なる初期値から開始しても同じ残差プロファイルに収束する

## ループ2：仕様改訂（外側・開発時）

**コーパス単位で回す。** 1音源だけで回すと、その音に過適合したエンジン仕様ができあがる。ジャンル・音色の異なるターゲットを10〜20個並べ、コーパス全体の残差プロファイルを見てから改訂する。

入力経路は2本ある。

1. **ループ1からの数値**：能力ギャップと判定された残差プロファイルの集積
2. **ループ3からの言語ログ**：ユーザーが到達できなかった履歴（自動判定不能、人間が定期的に読む）

出力は2つ。

- エンジン能力仕様の改訂（`docs/02-engine-spec.md` の更新＋ADR）
- マクロ軸設計の改訂（内部パラメータ空間 → DAW露出軸への写像）

### マクロ軸設計をここに置く理由

エンジン内部は数百の値を持つが、DAWに露出するのは十数個であるべきである。この写像（軸の切り出しと命名）は内部仕様が固まらないと決められないため、ループ2の出口に置く。

## ループ3：到達（実運用・人間が判定）

ループ1と決定的に違うのは、**参照信号が存在しないため残差が計算できない**点である。オラクルが指標ではなく人間の耳になる。

### 仕様化ループではなく選好抽出ループとして設計する

人間は音を言葉で記述するのは苦手だが、二つ並べて弁別するのは得意である。したがって：

- ❌ 「もっと硬く」を単一のパラメータ変更として解釈し、1案を返す
- ✅ **変化方向の異なる候補を2〜3個生成し、ユーザーに選ばせる**

曖昧な形容詞を、ユーザーが得意なA/B弁別タスクに変換する。周回数の予算が数回しかない以上、1周あたりの情報利得を最大化する設計が要る。

選択の履歴はユーザー個人の語彙辞書として蓄積し、次セッションの初手精度に反映する。

### 到達失敗時の切り分け

ユーザーがイメージに到達できなかったとき、原因は2つある。

- **マクロ軸の設計ミス**：エンジンには表現力があるが、露出した軸が求める方向とズレている → ループ2のマクロ設計へ
- **エンジンの能力不足** → ループ2の仕様改訂へ

このシグナルは数値ではなく言語なので**自動判定できない**。`docs/log/capability-gap-log.md` に蓄積し、非同期で読む。

## 責務の分担線

| 担当 | ノード |
|---|---|
| **LLM** | 分析スキルの実行、パラメータ推定、残差の切り分け、仕様改訂の起案、意図の解釈 |
| **バイナリ（C++等）** | シンセエンジン、ヘッドレスレンダラ、VSTプラグイン、GUI |
| **ハーネス（スクリプト）** | 指標算出、CIリグレッション、コーパス実行 |
| **ユーザー** | 音源と意図の入力、A/B弁別、最終判定 |

### ヘッドレスレンダは必須

GUIを立ち上げてDAWで手動バウンスしていてはループ1が回らない。プリセットを食わせてWAVを吐くCLIを、プラグイン本体と**同じエンジンコアから**ビルドする。エンジンコアはプラグインフレームワークに依存しない層として切り出すこと。

### 評価器はCIと共用する

ループ1の客観評価器と、CIのリグレッションテストは**同じものである**。ゴールデンWAVを置き、コミットごとにレンダして指標を測る仕組みは、フィッティングの評価器そのものになる。二度作らないこと。

これがフェーズ0で最初に作るものであり、これがないとPRのエビデンスが成立しない。

## 中間プリセットの受け渡し

LLM側とVST側の境界は中間プリセットファイルである（スキーマは `docs/03-preset-format.md`）。

プル型／プッシュ型のどちらでもよいが、**フェーズ0〜2ではファイル変更検知の仕組みは作らない**。CLIレンダラに引数でパスを渡すだけで足りる。変更検知が必要になるのはフェーズ4以降、GUI上でのライブ編集を扱うときである。先回りして作らないこと。
