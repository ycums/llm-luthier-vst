## 背景

「**どの環境でビルド・テストが通れば、ビルドできたと言ってよいのか**」を決定として記録する（Issue #66）。

PR #64 の直接の原因は `/utf-8` の欠落だったが、根本原因はこの決定が存在しなかったことにある。
`docs/adr/0006` は CMake 採用の利点として「GitHub Actions（Linux/macOS/Windowsランナー）でのサポートも
標準的」と*言及*しているだけで、**サポート対象そのものを決定として書いていない**。ジェネレータも
「指定せず環境の既定に委ねる」としていた。決定がない以上、下流のIssueの完了条件も「CIで実行される」
としか書けず、単一環境のCI成功で完了と主張できてしまう——実際 Issue #51 はそう書かれており、
PR #64 はそれを正直に満たしたまま Windows（日本語ロケール＝cp932）で壊れていた。この事象は
`docs/log/session-log.md` の **S-002** として記録されている。本ADRはその S-002 を根拠として、
サポート対象とCI検証範囲を確定させる。

本ADRのスコープは **ヘッドレスのエンジンコアとCLI**（`docs/adr/0006` と同じく、責務分担表の
「バイナリ（C++等）」のうち VSTプラグイン本体を除く部分）に限る。ハーネス（Python、`docs/adr/0003`）や
GUI・プラグイン層（フェーズ4）は対象外であり、将来プラグイン層を足す際に対象プラットフォームは
増えうる（本ADR末尾「将来への注記」参照）。

## 対象の定義に含めるもの：ロケール／コードページ

「対象プラットフォーム」を OS とコンパイラの組だけで定義すると、実測で確認された
`test-windows` の検出能力の限界（Issue #67）が定義から漏れる。**本ADRではロケール／コードページを
対象の定義に含める。**

背景：今回の破綻は日本語ロケール（cp932）の MSVC が UTF-8 ソースを Shift-JIS と誤解し、
行コメント末尾の `0x5C`（バックスラッシュ）衝突で行継続が起きてパースエラーに連鎖したもの。
一方 GitHub の `windows-latest` は英語ロケール（cp1252、単一バイト符号化）であり、`0x5C` 衝突が
起きない。Issue #67 の実測（PR #70 の検証ブランチ、run `34005656814`）で、`/utf-8` を外しても
`test-windows` はビルド・147テストすべてに成功することが確認された。

**したがって「`test-windows` が Windows ビルドを守っている」と書くことはできない。** 守られているのは
cp1252 環境に限る。ローカル日本語ロケール（cp932）のMSVCは `test-windows` の検証範囲の外にあり、
`engine/CMakeLists.txt` の `add_compile_options(/utf-8)`（ロケールに関係なく常に効く）が唯一かつ
現時点で正しい対処である。

## 決定

### 1. サポート対象プラットフォーム／コンパイラ（決定の本体）

エンジンコアとヘッドレスCLI（以下「対象」）のサポート対象は次の2つとする。

| OS | コンパイラ | サポート | CIで検証 | 備考 |
|---|---|---|---|---|
| Linux | GCC（`ubuntu-latest` が提供するもの） | 対象 | する（`metrics.yml` metrics[ubuntu]。〔改訂〕旧 `ci.yml` test は重複のため廃止、下記「7.」） | 開発・CIの基準環境 |
| Windows | MSVC（`windows-latest` が提供するもの） | 対象 | する（`ci.yml` test-windows） | `/utf-8` を明示（cp932起因の破綻を回避）。〔改訂〕指標算出（`metrics.yml` の Windows ジョブ）は行わない、下記「7.」 |

- **candidate はサポート対象外だが、開発環境として維持する**（下記「3. MSVCかMinGW-w64か」参照）。
- **macOS（clang）はフェーズ1のサポート対象に含めない**（下記「4. macOSを含めない理由」参照）。
- OS とコンパイラの組だけでなく、**ロケール／コードページも対象の定義に含める**（上記「対象の定義に
  含めるもの」）。Windows のサポートは「英語ロケール（cp1252）でビルド・テストが通ること」をCIで検証し、
  「日本語ロケール（cp932）では /utf-8 を明示することで通ること」を方針として保証する。cp932のコンパイルを
  CIで再現する仕組みは現時点で導入しない（下記「6. #67の検出手段3案の採否」）。

### 2. CIで検証するもの（対象に含めてCIで回さないものはない）

サポート対象として宣言した2組（Linux/gcc、Windows/MSVC）は、**いずれもCIでビルド・テストを検証する**。
`ctest --test-dir engine/build --output-on-failure` の実行が「ビルド・テストを検証する」の実体であり、
その担い手は Linux/gcc が `metrics.yml` の `metrics[ubuntu]`、Windows/MSVC が `ci.yml` の
`test-windows` である（〔改訂・Issue #90〕もとは `ci.yml` の `test` と `test-windows` がその実体
だったが、`test`（ubuntu）は `metrics[ubuntu]` の真部分集合であることが実測で確認されたため統合した。
詳細は下記「7.」）。対象に含めてCIで回さない環境は存在しないため、「CIで回さない対象の検証をどう
担保するか」という類の問題はフェーズ1では発生しない。

「対象」を宣言したにもかかわらずCIで検証しない環境を持ち込むことは、S-002 が記録した失敗の再現
（検証した範囲を超えて完了を主張する）に直結するため、**フェーズ1では対象＝CI検証対象**に限定する。
対象とCI検証対象を分離する必要性は、それが実際に生じるまで導入しない（`AGENTS.md` 第8節の3回ルール）。
この原則は〔改訂・Issue #90〕でも変えない。指標算出（`run-corpus`）の実行有無はこの原則の対象外
であり、「対象＝CI検証対象」が指しているのは常に**ビルド・テスト**である（下記「7.」）。

### 3. MSVCかMinGW-w64か：MSVC を追認（PR #64 の決定を決定として記録）

PR #64 は Windows のコンパイラとして **MSVC** を選び、`/utf-8` を設定した。しかし MinGW-w64 を
対象外とする決定はどこにも書かれていなかった。`docs/adr/0006` はこの選択をP1-06に委譲しており、
本ADRで**MSVC を採用として追認**し、**MinGW-w64 をサポート対象外**とする。

- **採用：MSVC**。理由は次の3点。
  1. **決定論担保との整合**：`docs/adr/0006`「決定論・サンプルレート非依存の担保」は自動ベクトル化・
     FMA融合に依存しないスカラーループで信号生成を書く方針であり、コンパイラ間の出力差はソースの書き方で
     ではなく最適化フラグの扱いで制御される。`engine/CMakeLists.txt` は積極的な最適化フラグを追加せず
     コンパイラの既定に委ねている。したがって MSVC を選んでも、決定論担保の前提（スカラーループ）と
     矛盾しない。MinGW-w64 を選ぶことは他のどの前提も改善しない。
  2. **CIランナーとの整合**：GitHub Actions の `windows-latest` が既定で提供し、`ilammy/msvc-dev-cmd` で
     確実に再現できるのは MSVC である。`test-windows` は MSVC 前提で設定・検証済み。
  3. **将来のプラグイン化との整合**：VST3 SDK（Steinberg）は Windows で MSVC を第一級でサポートする
     （DLLのエクスポート・デバッグシンボル周り）。`docs/adr/0006` の「将来プラグイン層を足す際に地続きで
     拡張できる」方針に矛盾しない。
- **不採用：MinGW-w64**。上記3点のいずれも満たさないため。とくに VST3 プラグイン化（フェーズ4）との
  整合が不明瞭になる点は決定的である。

### 4. macOS（clang）をフェーズ1のサポート対象に含めない理由

macOS（clang）は**フェーズ1の対象に含めない**。

- 理由1（要求の不在）：対象（エンジンコア＋ヘッドレスCLI）は `corpus/manifest.json` の音源をレンダして
  指標を出すヘッドレス用途であり、OS特有の機能（macOSのAudioUnit等）に一切依存しない。macOSでビルド
  する実益は現時点で存在しない。
- 理由2（S-002再発の回避）：対象に含めながらCIで検証しないと、「サポート対象だが未検証」の環境が生まれ、
  S-002 が禁じた「検証した範囲を超えた完了主張」の温床になる。macOS のCIジョブを追加してまで対象化する
  実益が今はない。
- 理由3（フェーズ4で再決定が必須）：VSTプラグイン本体を mac のDAW（ロジック等）で動かすなら必ず
  必要になる。プラグイン層の設計・対象DAWが決まる**後続のADR**でサポート対象として再検討する
  （本ADR末尾「将来への注記」）。

### 5. CMake ジェネレータの扱い

- **ローカル**：`docs/adr/0006` どおり、ジェネレータは環境の既定に委ねる（Ninja推奨、Makefilesでも可）。
- **CI**：ビルドは**単一コンフィグ（Release）に固定**し、Windows では **Ninja を明示的に指定**する。
  `test-windows` が `ilammy/msvc-dev-cmd` で MSVC 環境を設定したうえで `-G Ninja` を指定しているのは、
  既定のVisual Studioジェネレータがマルチコンフィグでバイナリ配置を `Debug/Release` に分けてしまい、
  後続ステップ（`LUTHIER_RENDER_BIN` のパス解決、pytest からの呼び出し）が単一パスで済まないためである。
  このCI固有の選択を**決定として記録**し（`docs/adr/0006` の「環境の既定に委ねる」はローカル向けの記述と
  整理する）、ローカルの手動検証手順とも一致させる。

### 6. #67 が挙げた検出手段3案の採否（将来の `/utf-8` 除去を防ぐ仕組み）

Issue #67 は「`test-windows` はcp932起因の破綻を検出できない」ことを実測で確定し、ロケール非依存の
検出手段を3案挙げて採否の判断を本ADRに委ねた。

| 案 | #67 の評価 | 本ADRの採否 |
|---|---|---|
| `/utf-8` 指定の有無を検査する静的チェック（例：`compile_commands.json` のフラグ検証） | 検討対象 | **未採用**（トリガー付き） |
| Windows ジョブでコードページを日本語（cp932）に切り替える | 要検討 | **未採用**（トリガー付き） |
| C4819 をエラー扱いにする | 却下（cp1252ではC4819自体が出ないため効果なし） | **却下** |

**解釈の選択**：`AGENTS.md` 第8節の3回ルールの適用について、本ADRは次の読みを**明示的に選択**する。

- **「CIチェックの追加」は追加機能であり、3回ルールが適用される。** 同分類の失敗（日本語ロケールの
  MSVCがUTF-8ソースを誤解する、つまり「環境前提の未検証／完了条件の穴」）の観測は現時点で1件（S-002）
  であるため、**未採用**とする。S-003 は「完了の誤報告」で分類が異なる。Issue #67 が指摘するもう一方の
  読み（「既に2回測っている（ローカルでの失敗、CIが捕まえられないことの実測）ので導入してよい」）は、
  ローカル失敗とCI限界の実測を「同種の失敗2回」と数える。本ADRはこれを取らない。理由は、この2つは
  「失敗の発生」ではなく「失敗の同一事象の観測」であり、3回ルールが想定する「同じ種類の失敗・同じ手戻り
  が3回起きた」（`AGENTS.md` 第8節）とは性質が異なるため。**失敗はS-002の1件のみ**であり、閾値（3件）に
  達していない。
- **導入の引き金**：同じ分類の失敗が**あと2回**観測された時点で、上記3案のうち実現可能なもの
  （静的チェック、およびcp932を再現できるコードページ切替）を実装Issueとして起票する。C4819エラー化は
  cp1252では効果がないため、常に却下のまま。
- 現時点で `/utf-8` は main に残存しており（Issue #67 は検証用ブランチ限りで外し、main は無変更）、
  実害は閉じている。本採否は「将来の除去を防ぐ新しい仕組み」を今作るかどうかの決定であり、現状の
  ビルドは壊れていない。

### 7. CI検証範囲の見直し（Issue #90 改訂）：ジョブの重複と、本ADRが要求していない検証を取り除く

Issue #89（ADR非依存の即効策）を先に入れた後も残る、ADRの改訂を要する削減を本節で決定する。
根拠は請求通知（無料枠2,000分に対し1,811分＝90%消費）と、同一コミット `541afe9` に対する
実測（Issue #89 の表。出典：[ci run](https://github.com/ycums/llm-luthier-vst/actions/runs/34028452492) /
[metrics run](https://github.com/ycums/llm-luthier-vst/actions/runs/34028452487)）。

**削るのは2つとも「本ADR §1・§2が要求していない実行」である。** §1・§2 が要求するのは
「Linux/gcc・Windows/MSVCの2組でビルド・テストが通ること」だけであり、指標算出（`run-corpus`）
まで両OSで回すことも、同じ検証を複数ジョブで重複させることも要求していない。

#### (a) Windows での指標算出（`metrics.yml` の Windows ジョブ）をやめる

`metrics.yml` の Windows ジョブ（旧称 `metrics[windows]`）は 34分/コミット（全体の52%）を占める
最大の単一コストだが、その大半は指標算出（`run-corpus`）であり、§1 が求める「ビルド・テストが
通ること」ではない。Windows のビルド・テストは `ci.yml: test-windows`（16分）で引き続き検証する。
`metrics.yml` から Windows の matrix エントリを削除し、指標算出は Linux（`metrics[ubuntu]`）のみで行う。

#### (b) `ci.yml: test`（ubuntu）を廃止し `metrics[ubuntu]` に統合する

ステップ列を実測で比較すると、`ci.yml: test` は `metrics[ubuntu]` の**真部分集合**である
（configure / build / ctest / setup-python / uv / ruff / pytest はいずれも `metrics[ubuntu]`
にも含まれる）。Linux/gcc のビルド・テスト検証を `metrics[ubuntu]` に一本化し、`ci.yml` の
`test` ジョブは削除する。`metrics[ubuntu]` の `run-corpus`（指標算出）は #86（baseline鮮度検証。
ubuntu の run-corpus 出力を不変条件とする決定）の前提であり、**落とせない**。

#### 改訂後もビルド・テスト検証（§1）が維持されていることの対応表

| 検証項目 | 改訂前 | 改訂後 |
|---|---|---|
| Linux/gcc ビルド・テスト | `ci.yml: test` | `metrics.yml: metrics[ubuntu]`（`configure`/`build`/`ctest` を含み実体は同一） |
| Windows/MSVC ビルド・テスト | `ci.yml: test-windows` | 変更なし（`ci.yml: test-windows`） |
| Linux 指標算出（`run-corpus`） | `metrics.yml: metrics[ubuntu]` | 変更なし（#86 の前提のため必須） |
| Windows 指標算出（`run-corpus`） | `metrics.yml: metrics[windows]` | **廃止**（削減対象(a)） |
| C++ lint（clang-format/clang-tidy） | `ci.yml: lint-cpp` | 変更なし |

サポート対象＝CI検証対象（§1・§2）は Linux/gcc と Windows/MSVC のまま変わらない。変わるのは
「指標算出をどのOSで行うか」だけであり、「サポート対象だが未検証」の環境は生まれない
（Windows は改訂後もビルド・テストがCIで検証され続ける）。

#### Q-016（コンパイラ間のビット一致）との関係

Q-016（`docs/06-open-questions.md`）は「コンパイラ間（gcc/MSVC）のビット一致は保証しない」ことを
明示しており、未解決である。この未解決が `metrics[windows]` の要否にどう影響するかは、残す場合と
落とす場合で次のように異なる。

- **`metrics[windows]` を残す場合**：Q-016が未解決である以上、Linuxの指標とWindowsの指標が一致する
  保証はない。両者が食い違っても、それがコンパイラ差（libmの丸め）によるものかエンジンのバグに
  よるものか、指標の値だけからは区別できない。したがって両OSで指標算出を続けても「値が違う」という
  情報しか増えず、34分/コミットのコストに見合わない。
- **`metrics[windows]` を落とす場合（本改訂の採用）**：Windows側の責務を「ビルド・テストが通ること」
  （`ctest`。§1）に限定するため、Q-016の未解決は運用上の障害にならない。指標算出をLinux（基準環境、
  §1「開発・CIの基準環境」）に一本化することで、指標の解釈にコンパイラ差を持ち込まない。Q-016が
  将来解決した場合、Windows指標算出の再開を検討する余地は残す（下記「将来への注記」）。

#### 効果（実測ベースの見積り）

Issue #89 が測った同一コミットのジョブ別課金分（分。切り上げ・Windowsは×2課金込み）から、
削減対象(a)(b)を除いた場合の1コミットあたりの課金分を見積もる。

| ジョブ | 改訂前 | 改訂後 |
|---|---:|---:|
| `ci.yml: test`（ubuntu） | 4 | 0（`metrics[ubuntu]` に統合） |
| `ci.yml: lint-cpp`（ubuntu） | 2 | 2 |
| `ci.yml: test-windows`（windows、×2課金込み） | 16 | 16 |
| `metrics.yml: metrics[ubuntu]` | 9 | 9 |
| `metrics.yml: metrics[windows]`（windows、×2課金込み） | 34 | 0（廃止） |
| **計** | **65** | **27（-58%）** |

この見積りは各ジョブの実測値（Issue #89 の表）をそのまま使っており、ジョブ構成の変更のみを
反映した机上計算である。改訂後の実際のワークフロー（本ADRはコードを変更しない、下記「結果」）が
入った時点の1コミット分の実測値は、実装Issueで#89と同じ方法（同一コミットのジョブ別課金分を
Actions run から算出）で確認し、実装Issueの完了条件とする。

さらにFetchContent（Catch2/nlohmann-json）のキャッシュを入れた場合は約20分（-69%）まで下がる
見込みだが、これは実装量が大きいため本ADRでは決定せず、実装Issueで扱う候補とする
（下記「将来への注記」）。

### 8. 数値一致の保証範囲と baseline 鮮度検証の判定（Issue #107 改訂、#96 対応）

`docs/04-metrics.md`（#86 / #88）は、`corpus/baseline/` の鮮度検証を「`ubuntu-latest` での
CI実行に限り**ビット完全一致**」と定めていた。この前提は「基準環境（上記「1.」）の中なら指標値は
ビット一致する」ことだったが、#96 でそれが成り立たないことが実測された。本節は、どの層の値を、
どの範囲でビット一致として保証するかを決め直す。

#### (a) 観測（決定の前提）

**CI（#96 の[実測コメント](https://github.com/ycums/llm-luthier-vst/issues/96#issuecomment-5648330081)）**

- エンジンソース・`corpus/baseline/`・ランナーイメージ（ubuntu-24.04 `20260831.293.1`）・GNU 13.3.0 が
  すべて同一の2 run（[34054474598](https://github.com/ycums/llm-luthier-vst/actions/runs/34054474598) /
  [34055105958](https://github.com/ycums/llm-luthier-vst/actions/runs/34055105958)、12分差）が
  pass / fail に割れた
- 鮮度検証が実際に実行された run は #92 以降でこの2件と
  [34678164060](https://github.com/ycums/llm-luthier-vst/actions/runs/34678164060) attempt 2（pass）の
  **計3件のみ**。それ以外（34055466128 の attempt 1〜10、34154706536、34677047886、34677566429、
  34678164060 attempt 1）は課金停止でジョブ自体が起動していない
- 失敗 run では、両側とも値を持つ指標 152 件のうち **13件**が不一致。種類は
  `trajectories.transient_env_corr`（9音源）・`trajectories.f0_dist`（3音源）・
  `segments.attack.loudness_diff_db`（1音源）の3種のみで、差は相対 **2.4e-15 以下**（1〜18 ULP）。
  残る139件（全音源の `overall.msstft` / `overall.mfcc` / `bands` を含む）はビット一致した
- 成功した2 run（イメージ版もコミットも異なり6日差）の成果物 `metrics-vectors` は、レンダWAV 11件の
  SHA-256 と指標JSON 11件のバイト列が**完全一致**した。失敗 run はアップロード手順が鮮度検証より後に
  あるため成果物が残っておらず、そのWAVは観測できていない

**ローカル（スパイク。Windows 11 / AMD Ryzen 5 7600（AVX-512 対応）/ NumPy 2.4.6 /
scipy-openblas 0.3.31）**：入力を上記 34054474598 の Linux レンダWAVに固定し、CPU別カーネル選択の
設定だけを変えて全11音源の指標を算出した。

| 変えた設定 | 値が変わった指標（152件中） | 最大の相対差 |
|---|---|---|
| 同一設定での再実行 | 0 | — |
| `OPENBLAS_NUM_THREADS` 12 → 1 | 0 | — |
| `OPENBLAS_CORETYPE` 既定（SkylakeX）→ Cooperlake | 0 | — |
| `OPENBLAS_CORETYPE` 既定 → Haswell / Zen / Sandybridge / Nehalem | 8〜11（`transient_env_corr` と、一部で `overall.mfcc`） | 4.0e-15 |
| `NPY_DISABLE_CPU_FEATURES=X86_V3` | 2（`overall.mfcc`・`bands`） | 3.1e-16 |

- `tibetan_singing_bowl` の `transient_env_corr` は、AVX-512 カーネル（SkylakeX）で
  `0.20651689437128504`（**baseline の値**）、AVX2 カーネル（Haswell / Zen）で
  `0.20651689437128515`（**失敗 run の current の値**）となり、CIの2値をそれぞれ**ビット単位で再現**した
- OS をまたいだ絶対値は一致しない（同じ Linux レンダWAVを入力にしても、Windows で算出した
  `overall.msstft` は baseline と相対 4e-4 程度ずれる。原因は調べていない）。したがって Windows 上で
  baseline を生成・比較することはできず、上表は同一マシン内の相対比較としてのみ意味を持つ

**検出したい変化の最小の大きさ（スパイク）**：レンダWAVは IEEE float32 のため、エンジン出力の変化の
最小単位は「1サンプルを float32 で1刻み動かす」ことである。34054474598 の各レンダWAVで、1サンプル
（10ms 地点・中央の2箇所）を1刻み動かして指標を再算出したところ、22ケースすべてで8件以上の指標が
変化し（毎回 `overall.msstft` を含む）、ケースごとの最大相対変化は**最小 7.2e-11**だった。
この測定には次の偏りがある：現状のプリセットは10音源が共通の暫定プリセット
（`corpus/presets/provisional_v0.json`）で、レンダWAVは実質2種類しかない（ターゲット側は11種類）。
また動かしたサンプルの振幅は、10音源で 2.5〜4.0、`spoken_hello` で 0.036〜0.37 と大きめである。

#### (b) 層の切り分けの結論

- **(ii) ハーネス側（指標算出）で ULP 差が生じる機構は実在する**：NumPy / OpenBLAS は実行時に CPU に
  応じて演算カーネルを選び、その選択だけで `transient_env_corr`（`np.corrcoef`）の最終桁が変わる。
  CIの1値を正確に再現した。GitHub ホステッドランナーの CPU が run ごとに異なりうることと整合するが、
  **ランナーの CPU 型番はログに出ておらず、失敗 run が AVX-512 非対応機だったことは未確認**である
- `f0_dist`（`librosa.pyin`）と `segments.attack.loudness_diff_db` の差は、ローカルで変えられた
  どの設定でも**再現しなかった**。原因は未特定（Linux 版 NumPy にしかない CPU 別実装などが候補だが
  未検証）
- **(i) エンジン側は、失敗 run について直接観測できていない**（WAV が残っていない）。間接的には、
  1刻みの変化でも毎回動く `overall.msstft` が失敗 run の全音源でビット一致しており、WAV も同一だった
  可能性が高い。ただし小さな振幅のサンプルだけが変わった場合などは排除できない。
  `GLIBC_TUNABLES` で libm の CPU 別経路を切る実験は、本決定の作業環境に Linux が無く**実施していない**

#### (c) 決定

1. **エンジンのレンダWAVの決定論（`docs/02-engine-spec.md`「同じプリセット・同じseedから常に
   ビットレベルで同一のWAV」）は変更しない。** 保証範囲は Q-016(4) のとおり「同一ビルド・同一環境」の
   ままとする。CPU の異なるマシン間での WAV のビット一致は、上記(a)で2 run の一致を観測したにとどまり、
   保証としては追加しない。`docs/02` を変えないため、本改訂は仕様変更PRではない
2. **ハーネスが算出する指標値は、マシン（CPU）をまたいだビット一致を保証しない。** ランナーイメージ・
   依存パッケージ・入力WAVが同一でも、NumPy / OpenBLAS の CPU 別カーネル選択により最終桁が変わる
   ためである（(a) ローカル表）。ビット一致を期待してよいのは、同一マシン・同一設定での再実行に限る
3. **baseline 鮮度検証の判定を、ビット完全一致から次の許容誤差付き比較に変える。**
   両側とも値を持つ指標について `math.isclose(baseline, current, rel_tol=1e-12, abs_tol=1e-12)`
   が偽のとき不一致とする。欠測の有無の食い違い（片方だけ `null`）と、baseline 側にエントリが無い
   場合は、従来どおり許容誤差なしで不一致とする。検証を `ubuntu-latest` のジョブに限る点は変えない
   - **`rel_tol=1e-12` の根拠**：観測したノイズの最大（CI 2.4e-15、ローカル 4.0e-15）の約250倍、
     検出したい最小の変化（1サンプル1刻みで 7.2e-11）の約1/70 に置く。両端の間（約4桁）の
     対数上のほぼ中央である
   - **`abs_tol=1e-12` の根拠**：`transient_env_corr` のように 0 付近をとりうる指標では相対差が
     発散するため、絶対差の下限を併用する。絶対値1未満の指標で観測したノイズの絶対差は最大
     9.4e-16 で、その約1000倍に置く。`abs_tol` が効くのは値の絶対値が1未満のときだけであり、
     それより大きい値の判定は `rel_tol` で決まる
   - **この許容誤差で検出できないもの**：振幅の非常に小さいサンプルだけが変わるような、1サンプル
     1刻みより更に小さい変化。実際の DSP 変更は多数のサンプルを動かすため問題にならない見込みだが、
     保証ではない
   - **許容誤差で吸収できないもの**：ノイズが ULP 差ではなく離散的な飛び（例：`pyin` の有声判定が
     境界で反転する）として現れた場合は、本許容誤差では通らない。そのときは値を広げて黙らせず、
     実測を Q-016 に追記して本節を改訂する
4. **CI 上の「決定論の確認」は、指標JSONではなくレンダWAVのバイト列で行う。** `metrics.yml` の
   `Compute vectors checksum` は Issue #13 の完了条件「出力JSONがビット単位で一致する」の確認材料と
   されてきたが、2. により、別 run（別マシン）間の指標JSONの一致は保証対象ではなくなる。エンジンの
   決定論（1.）の確認には `renders/*.wav` のハッシュを用いる
5. **鮮度検証が失敗した run が、原因の切り分けに必要な証拠を残すようにする。** #96 では、
   ランナーの CPU 型番がログに無く、失敗 run の成果物（WAV・指標JSON）も残らなかったため、
   層の切り分けが推定にとどまった。実行 CPU の型番・命令セットと NumPy / OpenBLAS の実行時構成を
   ログに出し、成果物は鮮度検証の成否に関わらずアップロードする

実装（`harness/baseline_freshness.py`・テスト・`.github/workflows/metrics.yml`、および実装に
合わせた `docs/04-metrics.md`「一致の判定方法」の書き換え）は、本改訂の確定後に実装Issueで行う。
本改訂自体はコードを変更しない（`docs/04-metrics.md` には、判定方法が本節で改訂されたことを示す
注記だけを加える）。

## 検討した案（採用しなかった案とその理由）

`docs/adr/README.md`「採用しなかった案とその理由を必ず書くこと」に従い、本決定に至るまでに検討した
が採用しなかった案を以下に記載する。

### 案1：ubuntu（Linux/gcc）のみに対象を絞る

- **却下理由**：PR #64 で実際に Windows/MSVC が壊れていたのは事実であり、`test-windows` が無ければ「ubuntuで
  通るからビルドできる」がWindowsの破綻を隠す。`docs/adr/0003` がハーネスをクロスプラットフォームにした
  前提、および将来のVSTプラグイン（Windows DAW）を見据えると、Windowsを対象から外す利点は検証コストの
  削減のみで、S-002が記録した破綻の再発確率をむしろ高める。対象2つにするためのCI時間の増分は小さい。

### 案2：macOS（clang）を対象に含め、CIで回す（ビルド時間を払う）

- **再検討時点まで導入しない**（上記「4. macOSを含めない理由」）。macOSのCIジョブを追加すると
  `ci.yml` が3ジョブになり、VSTプラグイン層の設計が決まっていない段階でのビルド・テストは投資対効果が
  低い。プラグイン層の設計が決まる後続ADRで、macOSを対象に含めるかを改めて決定する。

### 案3：対象に含めるがCIでは回さない（例：macOSを対象に含めてCIはubuntu/windowsのみ）

- **却下理由**：S-002 が禁じた「検証した範囲を超えた完了主張」の温床になる。対象とCI検証対象を分離する
  便益は、その分離の必要性が実測で生じるまで導入しない。フェーズ1では対象＝CI検証対象に限定する。

### 案4：WindowsのコンパイラをMinGW-w64にする

- **却下理由**：上記「3.」参照。MSVCを選ぶ理由（CIランナー・VST3互換・決定論担保との整合）のどこも
  MinGW-w64では満たせない。

### 案5：ジェネレータを全環境で可変のままにし、CI固有のNinja固定を決めとして残さない

- **却下理由**：`test-windows` が `-G Ninja` に固定したのは、Visual Studioジェネレータのマルチコンフィグ
  がバイナリ配置を `Debug/Release` に分けるからであり、後続のパス解決・pytest呼び出しを単純に保つため
  （上記「5.」）。この選択を決めとして記録しないと、別の環境でジェネレータを変えたときにパス解決が壊れ、
  S-002と同型の「環境前提の穴」になる。

### 案6：#67の検出手段3案のうち、静的チェックを今すぐ実装する

- **却下理由**：上記「6.」参照。3回ルールの適用について本ADRが選ぶ読み方では、同種失敗は1件（S-002）で
  あり、「先回りして環境を整えない」（`AGENTS.md` 第8節）に該当する。導入は引き金（あと2回）に委ねる。

### 案7（Issue #90）：`metrics[windows]` を残す（現状維持）

- **却下理由**：上記「7.」の「Q-016との関係」参照。Q-016が未解決のため、両OSの指標が一致する保証が
  そもそも無い。一致しない可能性のある値を2環境で出し続けても得られる情報は増えない。Windowsで必要な
  「ビルド・テストが通ること」は `ci.yml: test-windows`（16分）で満たされており、指標算出の34分/コミット
  はそれに対して不要なコストである。

### 案8（Issue #90）：`ci.yml: test`（ubuntu）を残す（`metrics[ubuntu]` との重複を容認する）

- **却下理由**：ステップ列の実測比較で `ci.yml: test` が `metrics[ubuntu]` の真部分集合であることが
  確認されている（上記「7.」）。重複を残す実益はなく、4分/コミットが純粋な無駄になる。

### 案9（Issue #90）：`ci.yml: test-windows` も削り、Windowsのビルド・テスト検証を `metrics.yml` に一本化する

- **却下理由**：本Issueのスコープ外である「Windowsでのビルド・テストの停止」に実質的に踏み込む
  （ジョブの器を変えるだけでも、ビルド・テストの成否判定を指標ジョブに混在させることになる）。
  `metrics.yml` は Q-006 の暫定方針により**指標の値がどうあれワークフロー自体を失敗させない**設計
  （ヘッダコメント参照）であり、ビルド・テストの成否判定（`ctest` の失敗）をこの設計の上に混在させると、
  「このジョブの失敗が指標の問題なのかビルド・テストの問題なのか」が曖昧になる。ビルド・テストの検証は
  専用の軽量ジョブ（`ci.yml: test-windows`）に残す。

### 案10（Issue #90）：FetchContentキャッシュや `push: main` の重複実行削減を本ADRで同時に決定する

- **却下理由**：Issue #90 の完了条件・スコープ外節のとおり、実装量を伴う施策の採否はADR確定後の
  実装Issueに送る（`AGENTS.md` 第5節「仕様変更を含むPRでの実装変更は不可」）。本ADRはこれらの採否を
  決めない（下記「将来への注記」）。

### 案11（Issue #107）：baseline を `ubuntu-latest` 上で再生成し、生成環境と検証環境を揃える（#96 提案1）

- **却下理由**：#96 の失敗は、baseline の生成環境と検証環境の違いでは説明できない。同一イメージ
  バージョンの2 run が pass / fail に割れており（上記「8.」(a)）、CI で再生成した baseline も、
  次の run が別の CPU に割り当たれば同じように不一致になりうる。

### 案12（Issue #107）：ランナーイメージのバージョンを固定する（#96 提案3）

- **却下理由**：案11と同じ。割れた2 run はイメージバージョンが同一だった。イメージを固定しても、
  (b) で確認した CPU 別カーネル選択は止まらない。

### 案13（Issue #107）：CPU 別カーネル選択を環境変数で固定し、ビット完全一致を維持する

`OPENBLAS_CORETYPE` や `NPY_DISABLE_CPU_FEATURES` を CI とローカルの双方で固定し、どの CPU でも
同じ演算カーネルを使わせる案。

- **却下理由**：(1) `f0_dist` と `segments.attack.loudness_diff_db` の差はローカルでどの設定を
  変えても再現せず、固定すべき設定の一覧が分かっていない。一覧が不完全なまま「ビット一致」を
  保証すると、#96 と同じ誤検出を別の指標で繰り返す。(2) GitHub ホステッドランナーの CPU は選べず、
  固定が全 CPU で効くことを検証する手段がない。(3) baseline を更新する開発者のローカル環境にも
  同じ設定を課すことになり、S-006 が示した「文書化された手動手順は守られない」問題を再生産する。

### 案14（Issue #107）：許容誤差を相対 1e-9 にする（#96 本文の例示）

- **却下理由**：根拠のない値である。(a) の実測では、1サンプル1刻みの変化による最大相対変化は
  7.2e-11〜1.0e-5 で、22ケース中10ケース（10ms 地点の11ケース中10）が 1e-9 を下回る。1e-9 では
  エンジン出力が実際に変わっても検出できない場合がある。

### 案15（Issue #107）：鮮度検証を指標値ではなくレンダWAVのハッシュ比較に置き換える

- **却下理由**：(1) 指標算出コード（`harness/metrics.py`）の変更による陳腐化を検出できない。
  baseline として持ち回っているのは指標JSONであり、WAVではない。(2) CPU の異なるマシン間での
  WAV のビット一致は保証していない（「8.」(c) 1.）ため、エンジン側に同種の問題が潜んでいれば
  同じ誤検出が起きる。(3) baseline の形式変更を伴う。WAV のハッシュは決定論の確認（(c) 4.）に使う。

### 案16（Issue #107）：鮮度検証が失敗したら再実行し、一度でも通れば成功とみなす

- **却下理由**：本当の陳腐化も「たまたま通るまで再実行」で隠れうるうえ、課金を伴う再実行を
  前提にする。どの run でも同じ判定になる比較方法を選ぶべきである。

  上記「7.」）があるが実装量が大きく、後者は #86（baseline鮮度検証）の main 実行前提との整合を
  #86 の実装確定後に判断する必要があるため、いずれも本ADRでは採否を決めない。
- **〔改訂・Issue #107〕`diff-corpus` の「悪化」判定も同じ ULP 差の影響を受ける。**
  `harness/metrics_diff.py` は値の大小を許容誤差なしで比べるため、CPU 別カーネル選択による最終桁の
  差が「⚠ 悪化」として表示されうる。これは Q-006（CIで指標悪化をブロックするか）の閾値の問題で
  あり、本改訂では扱わない。フェーズ2で指標差分を合否に使う前に、Q-006 側で決める必要がある。
- **〔改訂・Issue #107〕許容誤差（「8.」(c) 3.）の根拠は、CI 3 run とローカル1台の観測に基づく。**
  鮮度検証の失敗で、相対 1e-12 を超えるが実際の陳腐化とは考えにくい差が観測された場合は、値を
  広げて黙らせず、実測を Q-016 に追記して「8.」を改訂する。
- **〔改訂・Issue #107〕Windows 上では baseline を生成・検証できない。** OS をまたいだ指標値の差
  （「8.」(a)、相対 4e-4 程度）は許容誤差を大きく超える。`docs/04-metrics.md` の更新手順
  （`run-corpus` を実行して `corpus/baseline/` をコミットする）は、Linux 環境での実行を暗黙の
  前提にしている。この前提の明文化、または CI 成果物から baseline を取り込む手順は、本改訂では
  決めない。

## 結果

- 本ADRはコードを追加・変更しない（`AGENTS.md` 第5節「仕様変更を含むPRの実装変更は不可」によるメタADR）。
  ワークフロー（`.github/workflows/ci.yml` / `metrics.yml`）の変更は、本ADR確定後に起票する実装Issueで行う。
- サポート対象＝CI検証対象は Linux（gcc）と Windows（MSVC）の2つ。macOS・MinGW-w64・C4819エラー化は
  却下。MSVCを追認、`/utf-8` を明示、CIは単一コンフィグ（WindowsはNinja）で固定。
- `#67` の検出手段3案は「識別済みだが未採用」とし、導入の引き金（同種失敗あと2件）を記録した。
- **〔改訂・Issue #90〕** ビルド・テスト検証の担い手を、Linux/gcc は `ci.yml: test` から
  `metrics.yml: metrics[ubuntu]` に統合し、Windows/MSVC は `ci.yml: test-windows` のまま変更しない
  （上記「7.」対応表）。指標算出（`run-corpus`）は Linux（`metrics[ubuntu]`）のみで行い、Windows
  （`metrics[windows]`）では行わない。見積りで1コミットあたりの課金分は65分から27分（-58%）に減る。
- 本決定の根拠は `docs/log/session-log.md` の S-002（および後続の S-003）と、Issue #90 が引用する
  請求通知・ジョブ別実測（Issue #89 の表）である。
- 下流のIssue（#52〜#57）の完了条件は、本ADRの「サポート対象＝CI検証対象」の定義に従うことになる。
  本ADR確定後の実装Issueは、上記「7.」の対応表に従って `.github/workflows/ci.yml` と `metrics.yml`

  鮮度検証は `math.isclose(rel_tol=1e-12, abs_tol=1e-12)` による比較に変える（欠測の食い違いは
  従来どおり不一致）。エンジンのレンダWAVの決定論（`docs/02`）とその保証範囲（Q-016(4)）は変えない。
  決定論の確認はレンダWAVのハッシュで行い、鮮度検証が失敗した run は CPU 情報と成果物を残す。
  実装は #107 確定後の実装Issueで行い、#96 はその実装PRで閉じる。
