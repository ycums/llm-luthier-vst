# 0001. アーキテクチャ決定をADRとして記録する

- **状態**：Accepted
- **日付**：2026-09-05

## 背景

本プロジェクトは、エンジン仕様を観測に基づいて反復的に改訂する（ループ2）。改訂が繰り返されるため、「なぜ現在の仕様がこうなっているか」が失われやすい。

特に危険なのは、過去に検討して却下した案を、理由を忘れて再検討することである。ループ2の周回コストが数日単位であるため、この手戻りは高くつく。

## 決定

仕様・構造に関する決定をADRとして `docs/adr/` に記録する。採用案だけでなく、**却下した案とその理由**を必ず併記する。

## 結果

- 仕様変更PRにはADRが伴うため、PRが1つ増える
- 却下理由が残るため、同じ検討の反復を避けられる
- `docs/06-open-questions.md` の項目が resolved になった経緯を追跡できる
