# 0006. エンジンコアの実装言語・ビルド方式・テスト方式

- **状態**：Accepted
- **日付**：2026-09-05

## 背景

`docs/00-vision.md` のフェーズ1（最小エンジン）に着手するには、エンジンコアの実装言語・ビルド方式・テスト実行方式を決める必要がある。`AGENTS.md` 第6節により外部ライブラリ（ビルド系・テストフレームワーク・DSPライブラリのいずれも該当）の新規追加はADRと承認を要するため、これを済ませないと P1-06 以降のすべての実装Issueが「未承認のライブラリを使った実装」になる。フェーズ0の #1（`docs/adr/0003`）と同じ位置づけのゲートである。

あわせて `docs/01-architecture.md`「エンジンコアはプラグインフレームワークに依存しない層として切り出す」と `docs/02-engine-spec.md`「実装上の制約」を、具体的なディレクトリ構成・依存の向きとして確定する。VSTプラグイン本体はフェーズ4まで作らないが（Q-008 GUIフレームワーク選定は未解決のまま着手してよい）、コアの切り出し方を先に決めないと、プラグイン化の時点でコアの作り直しになる。

対象はエンジンコア・ヘッドレスCLIレンダラ（`docs/01-architecture.md` の責務分担表でいう「バイナリ（C++等）」行のうち、VSTプラグイン本体を除く部分）のみ。ハーネス（Python）は `docs/adr/0003` で決定済みでありスコープ外。

## 検討した案

### 実装言語

#### 案A：C++20（採用）
- 利点：VST3 SDK（Steinberg）自体がC++で提供されており、将来のプラグイン化（フェーズ4）で作り直しが発生しない。リアルタイム制約のあるレンダリングに実績が厚い。`docs/01-architecture.md` は既に責務分担表で「バイナリ（C++等）」と記述しており、本ADRはその想定を確定させるものである
- 欠点：メモリ安全性は自己責任。ビルド設定・依存管理がスクリプト言語より重い

#### 案B：Rust
- 利点：メモリ安全性、パッケージ管理（Cargo）の簡便さ
- **却下理由**：VST3ホスティング・プラグイン化のエコシステム（`nih-plug`、`vst3-sys`等）はC++のJUCE等と比べて発展途上であり、フェーズ4での統合方針（Q-008未解決を含む）に対して選択肢を先に狭める。DSPライブラリの成熟度も、ハーネス選定時（`docs/adr/0003`）にPython/Rustを比較した際と同様、C++に一日の長がある

#### 案C：C
- 利点：最小限のランタイム、あらゆるプラットフォームでの実績
- **却下理由**：`docs/02-engine-spec.md` の4層構成・モジュレーションマトリクスは型を使った構造化（層ごとのインタフェース、パラメータ経路の抽象化）と相性がよく、C++のクラス・テンプレートなしで書くと可読性・保守性が大きく落ちる

#### 案D：Zig
- 利点：C/C++との相互運用性、ビルドの単純さ
- **却下理由**：VST3バインディングがほぼ存在せず、フェーズ4での自作コストが大きい。言語自体も本ADR時点で1.0未満であり、長期運用するプロジェクトの基盤に据えるリスクが高い

### ビルドシステム

#### 案E：CMake（採用）
- 利点：C++プロジェクトの事実上の標準。VST3 SDK・JUCE等の主要な音声プラグインフレームワークがいずれもCMake統合を公式に提供しており、フェーズ4でプラグイン層を追加する際に地続きで拡張できる。GitHub Actions（Linux/macOS/Windowsランナー）でのサポートも標準的
- 欠点：設定言語が独自でやや読みにくい

#### 案F：Meson
- 利点：設定の可読性、ビルド速度
- **却下理由**：主要な音声プラグインフレームワーク（VST3 SDK、JUCE）の公式統合がCMake前提であり、フェーズ4で二重管理になる

#### 案G：Bazel
- **却下理由**：セットアップ・学習コストがフェーズ1（コア＋CLIのみ）の規模に見合わない。モノレポの複数言語ビルドを統括する用途に強みがあるが本リポジトリはPython（ハーネス）とC++（エンジン）の2系統のみで、それぞれ独立にビルド・テストできれば足りる

### テストフレームワーク

#### 案H：Catch2 v3（採用）
- 利点：ヘッダオンリーに近い構成でCMakeの `FetchContent` から導入でき、ビルド設定が軽い。BSL-1.0（Boost Software License、permissive）。DSP・音声プラグイン領域での採用実績が厚い
- 欠点：モック機構は持たない（本フェーズでは不要）

#### 案I：GoogleTest
- 利点：同等に有力な選択肢。モック（gMock）が必要になった場合に強い
- **却下理由**：本フェーズで必要なのは既知解フィクスチャに対する解析的な検証（Q-013、`docs/06-open-questions.md`）であり、モックは不要。ビルド時間・依存の重さでCatch2に劣る。決定的な優劣差ではないため、必要になれば後日ADRで見直す

#### 案J：自前の最小テストランナー
- **却下理由**：アサーション失敗時の診断表示（期待値・実測値の整形出力）を自作するコストが、成熟したフレームワークを導入するコストを上回る

### JSONパーサ（中間プリセット読込用）

#### 案K：nlohmann/json（採用）
- 利点：ヘッダオンリー、MITライセンス、事実上の標準。`docs/03-preset-format.md`「未知のフィールドを見つけたエンジンはエラーで停止する」を実装するのに必要な、オブジェクトのキー列挙・型検査のAPIが揃っている
- 欠点：大きなプリセットに対するパース速度はRapidJSON等より遅いが、v0のプリセットサイズ（`docs/03` 未確定：時系列の点数上限はあるが小規模を想定）では問題にならない

#### 案L：RapidJSON
- 利点：パース速度
- **却下理由**：DOM APIが低レベルで、未知フィールド検出のようなスキーマ的検証を自前で組む手間が大きい。v0では速度よりAPIの書きやすさを優先する

#### 案M：自前のJSONパーサ実装
- **却下理由**：`docs/03` の入れ子構造（Timeseries、layers、modulation.routes）をスクラッチで正しくパースする実装コストとバグ混入リスクが、成熟した既存実装を使う利点を上回る

### WAV書き出し

#### 案N：自前実装（採用）
- 利点：canonical PCM WAVの書き出しは数十行で決定論的に実装でき、外部依存を増やす必要がない。ハーネス側（`docs/adr/0003` で `soundfile`/libsndfile を採用）と異なり、エンジン側は読み込みを必要とせず書き出し専用であるため要件が小さい
- 欠点：将来ビット深度・チャンネル構成が増えた場合は自前で拡張する必要がある（v0はモノラル・16-bit PCMまたはfloat32を想定。具体形式はP1-06で決める）

#### 案O：libsndfile直接リンク
- **却下理由**：LGPLであり、静的リンクを避けるかLGPL条項（再リンク可能性の確保）を満たす配布上の配慮が必要になる。書き出し専用の単純な用途に対して過剰

## 決定

### 実装言語

**C++20**（案A）。

### ビルドシステム

**CMake 3.21以上**（案E）。ジェネレータは指定せず環境の既定（Ninja推奨、Makefilesでも可）に委ねる。

- 成果物の置き場所：`engine/build/`（ビルドディレクトリ、`.gitignore` に追加）。CLI実行ファイルは `engine/build/cli/luthier-render`（プラットフォーム依存の拡張子を含む）
- CIでのビルド手順（実際の導入はP1-06。ここでは方針のみ確定）：`cmake -S engine -B engine/build -DCMAKE_BUILD_TYPE=Release` → `cmake --build engine/build` → `ctest --test-dir engine/build --output-on-failure`

### テストフレームワーク

**Catch2 v3**（案H）を `FetchContent` で導入する。実行コマンドは `ctest --test-dir engine/build --output-on-failure`。

- **pytestとの並存**：C++側の単体テスト（DSP・パーサ・レンダリングの決定論性）は `ctest` で、ハーネス側（Python）の単体テストは引き続き `pytest` で、それぞれ独立に実行する。両者を1コマンドに統合しない（責務が異なるため、`AGENTS.md` 第5節「責務1つ」の精神に合わせる）。CLIバイナリの入出力を検証するE2Eテストは、ビルド済みバイナリを `subprocess` から呼ぶ形でpytest側に置く（P1-07以降、`docs/adr/0003` の延長）

### 外部ライブラリ

| ライブラリ | 用途 | ライセンス | 導入方法 |
|---|---|---|---|
| Catch2 | エンジンコアの単体テスト | BSL-1.0 | CMake `FetchContent` |
| nlohmann/json | 中間プリセットJSONの読込・検証 | MIT | CMake `FetchContent` |

いずれもpermissiveライセンスであり、`docs/adr/0003` で採用したハーネス側ライブラリの方針（コピーレフト回避）と整合する。WAV書き出しは自前実装のため外部ライブラリを追加しない。

## ディレクトリ構成と依存の向き

```
engine/
  CMakeLists.txt        # トップレベル。add_subdirectory(core cli tests)
  core/
    include/luthier/     # 公開ヘッダ（layers, preset, render 等）
    src/                 # 実装
    CMakeLists.txt        # 静的ライブラリ luthier_core をビルド。他のどのサブディレクトリにも依存しない
  cli/
    src/main.cpp          # ヘッドレスCLIレンダラのエントリポイント
    CMakeLists.txt         # 実行ファイル luthier-render。luthier_core に依存
  tests/
    CMakeLists.txt          # Catch2ベースの単体テスト。luthier_core に依存
  plugin/                 # 予約領域。フェーズ4まで作成しない
```

依存の向きは一方向に固定する：`cli` → `core`、将来の `plugin`（フェーズ4）→ `core`。**`core` はプラグインフレームワーク（VST3 SDK、JUCE等）のヘッダを一切 include しない。** これにより Q-008（GUIフレームワーク選定）や将来のプラグインラッパー選定を、`core` の作り直しなしに後から決められる。

`engine/` はリポジトリルート直下に置き、`CMakeLists.txt` はルートに置かない。ハーネス（Python、`pyproject.toml` によるビルド）とエンジン（CMakeによるビルド）のビルド系統を明確に分離するため。

## ハーネスからの呼び出し方針

ハーネス（Python）は `engine/cli` でビルドされた `luthier-render` 実行ファイルをサブプロセスとして起動し、中間プリセットJSONのパスと出力WAVのパスを引数で渡す。P1-07で `corpus/manifest.json` の `candidate_path` seam をこの呼び出し結果に差し替える。ハーネスはビルド済みバイナリのパスを明示的な設定（環境変数または引数）で受け取り、ビルド手順自体をハーネス側に埋め込まない（責務の分離を保つ）。

## 決定論・サンプルレート非依存の担保

`docs/02-engine-spec.md`「実装上の制約」が要求する2点は、選んだ言語・ライブラリの組み合わせで次のように担保する。

- **決定論**（同じプリセット・同じseedからビットレベルで同一のWAV）：浮動小数点演算の結果がコンパイラ・最適化レベル間で変わりうる自動ベクトル化・FMA融合に依存せず、各層の信号生成をスカラーの単純なループで書く。ノイズ生成はプラットフォーム依存の `<random>` エンジン実装ではなく、エンジンコアに内蔵する決定論的PRNG（xorshift系を想定、具体アルゴリズムはP1-09で確定）を用いる
- **サンプルレート非依存**：すべての時間パラメータ（Timeseriesの `t`、`duration` 等）を秒単位で保持し、レンダ時に指定サンプルレートで離散化する。フィルタ係数（Formant filter bank等）もサンプルレートを引数として都度導出し、特定のサンプルレートを前提にした事前計算・キャッシュを行わない

この担保方針の妥当性は、P1-06での実装後にCIのリグレッションテスト（同一コミットに対する複数回ビルド・レンダの出力比較）で検証する。

## スコープ外（本ADRでは決めない）

- **GUIフレームワークの選定**（Q-008）。`core` がプラグインフレームワーク非依存である限り、後から決めても作り直しが発生しない
- **VSTプラグイン本体のビルド**（フェーズ4）。`engine/plugin/` は予約領域として構成のみ示す
- **合成方式の選定**（Q-001）。P1-03の範囲
- **CIワークフローファイルの追加**。実際にビルド・テストが存在してから追加する（`AGENTS.md` 第8節、P1-06の範囲）

## 結果

- 本ADRはコードを追加しない（`AGENTS.md` 第5節「仕様変更を含むPRでの実装変更は不可」により決定のみ）
- P1-06（#51）以降が上記の言語・ビルド・ディレクトリ構成でCMakeプロジェクトを起こす
- `docs/01-architecture.md`「エンジンコアはプラグインフレームワークに依存しない層として切り出す」は、上記のディレクトリ構成と依存の向きとして確定した
- Q-008（GUIフレームワーク選定）は未解決のまま持ち越す。本ADRはGUIフレームワーク・プラグインラッパー（JUCE等）の採否には一切触れておらず、`core` の独立性がその選択の自由度を保っている
