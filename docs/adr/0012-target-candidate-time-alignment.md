# 0012. target と candidate の時間整列（Q-019）

- **状態**：Accepted
- **日付**：2026-09-13
- **対応Issue**：#120
- **前提**：#113（Q-019 の観測、PR #121）、#45 の所有者決定（フェーズ2の着手条件を Q-019 の決定に置き換える、[#45 のコメント](https://github.com/ycums/llm-luthier-vst/issues/45#issuecomment-5649287829)）
- **決定の根拠**：所有者判断（[#120 のコメント](https://github.com/ycums/llm-luthier-vst/issues/120#issuecomment-5651990118)、2026-09-13）

## 背景

ゴールデン音源の target には、オンセットより前に無音または低振幅の信号だけが続く区間を持つものがある（Q-009 の観測表で −40dB オンセットが `spoken_hello` 221.8ms、`violin_pizzicato` 727.6ms、`kalimba_sample` 1385.1ms など）。一方、プリセットの時間軸はノートオンを0とし（`docs/03-preset-format.md`）、指標は target と candidate を同じ絶対時刻で比較している（`harness/metrics.py`）。target のファイル内のどこが candidate のノートオンに当たるかを、誰がどう決めるかが定まっていなかった（`docs/06-open-questions.md` Q-019）。

このずれは区間別指標に限らず、全体指標・軌跡指標にも誤差として入る（Q-019「暫定の扱い」）。整列を決めないままフィッティングに入ると、先頭のずれを音色差としてフィットすることになる。このため #45 の所有者決定で、Q-019 の決定がフェーズ2の着手条件になった。

#113 の観測で、Q-019 は次の3つに分けて整理された（Q-019「この観測で決まったこと・決まらなかったこと（#113）」）。

- (A) 整列をプリセットが持つか、ハーネスが持つか
- (B) ハーネスが持つ場合、target のオンセット前の区間を比較に含めるか
- (C) ずらし量（target のファイル内で candidate のノートオンに当たる時刻）をどう得るか

(A)(B) は #113 で結論を導いたが所有者の確認が済んでおらず、(C) は判定基準が観測できず決まらなかった。本ADRは、#120 の所有者判断を受けて3点を決定として記録する。

## 決定

### (A) 整列はハーネスが持つ

プリセットの `t` はノートオンを0とする規約（`docs/03-preset-format.md`「時系列の表現」）のまま変えない。ずらし量はプリセットの外に置く。

根拠（Q-019 (A)）：プリセットが先頭の無音を時系列で表現する案（候補 (1)）では、フィット済みプリセットに録音ごとの先頭無音（−40dB オンセットで `spoken_hello` 約0.22s、`kalimba_sample` 約1.39s）が入る。DAW でノートオンしてもその時間だけ鳴らず、「DAW上で演奏・調整・オートメーションできる形で手渡す」（`docs/00-vision.md`）に反する。#113 観測1では (1) と (2) の指標値の差は小さかったが、1音源・1プリセットの観測であり、(1) を採る根拠にも退ける根拠にもしていない。

### (B) target のずらし量より前は比較から外す

指標は、ずらし量で整列した target と candidate の組に対して算出する。target のずらし量より前の区間は比較に含めない。

根拠（Q-019 観測4、所有者判断 (B)）：(A) の規約の下では、プリセットはノートオン前に音を出さない。target のオンセット前の背景を、0で埋めた candidate と比較に含めると、どこまで追い込んでも下がらない残差が入る（音色差ゼロでも全体 `msstft` が `spoken_hello` 3.10、`kalimba_sample` 0.25）。この残差はエンジンに表現する場所がないため、`docs/05-glossary.md` の定義を字義どおりに当てると能力ギャップと区別できず、誤ってループ2へエスカレーションされうる。比較から外せば構造上生じない。

**長さの扱いは本ADRでは決めない。** 所有者判断 (B) により実装Issueで決める。target を切り出す、candidate を延ばすなどで比較する信号の長さが変わると、`loudness_diff_db` が長さの比だけで動く（Q-019 観測1：1.626 − 10·log10(52244/41600) = 0.636）。Q-014（レンダ長の導出）とも関係する。

### (C) ずらし量は所有者が聴いて11件すべてに付与し、前提データとして記録する

- ずらし量は、所有者が target を聴いて音源ごとに付与する。`corpus/manifest.json`（またはそれに準ずる注釈）に**前提データ**として記録する
- **全11件を所有者付与で統一する。** オンセットという事象がない `sine_440hz` / `white_noise` / `rain_light` にも、所有者が明示的に 0 を付与する。先頭が完全な0の3件（`violin_pizzicato` / `violin_vibrato` / `crash_cymbal`）にも、「先頭の非ゼロ標本」などの別定義を使わない。音源ごとにずらし量の定義が混ざると、コーパス単位で残差を比べるときに扱いの違いが残差に混ざるためである（Q-019 (C) の「組み合わせ」の帰結）
- **エージェントはずらし量の値を決めない。** 閾値検出・指標最小化などで得た値を、仮値や初期値としても記録しない。所有者が付与していない音源の値を補わない

#### `AGENTS.md` 第1節との関係

`AGENTS.md` 第1節の「あなたは音を聴けない」は、**エージェントの判断に対する制約**である。所有者が付与するずらし量は音質の判断（「近づいた」「自然になった」）ではなく、指標の入力となる**時刻のラベル（前提データ）**として扱う。値は記録として残るため、同じ値から指標を再現できる。

したがって、所有者付与のずらし量を指標算出に使うことは第1節に反しない。この解釈は所有者が付与した値を入力として使うことに限られ、第1節がエージェントに課す制約は変わらない。

## 検討した案と採用しなかった理由

### (A) の候補

| 候補 | 採用しなかった理由 |
|---|---|
| (1) プリセットが先頭の無音も時系列で表現する | フィット済みプリセットに録音ごとの先頭無音が入り、DAW でノートオンしても鳴らない時間ができる（`docs/00-vision.md` に反する） |

ハーネス側の候補 (2)（レンダラまたはランナが candidate を遅らせる）と (3)（指標側が target をずらす）のどちらで実装するかは、退けたのではなく実装側で決める（下記「スコープ外」）。

### (B) の候補

| 候補 | 採用しなかった理由 |
|---|---|
| target のオンセット前も比較に含める（candidate の先頭を0で埋める） | 上記「(B)」の根拠のとおり、(A) の規約の下で下がらない残差が入り、能力ギャップと区別できなくなる |

(B) の代償（Q-019 (B)）：ずらし量が実際より遅いと、その区間の target の音が評価されない。早いと背景の一部が比較に戻る。(B) の安全性はずらし量の精度に依存する。所有者判断が (B) を採ったことの帰結として、この代償は残る。

### (C) の選択肢（Q-019 (C) の1〜4）

| 選択肢 | 採用しなかった理由（所有者判断） |
|---|---|
| 1. 閾値検出を操作的な定義として採る | 閾値を選ぶ根拠が観測されていない。`violin_tuning` では −40dB と −30dB の閾値差だけでずらし量が 633.6ms 動く |
| 3. 評価のたびに指標を最小にするずらし量を探す | #113 観測5で、最良のずらし量が指標ごとに割れ（全体 `msstft` +50ms、全体 `mfcc` と `transient_env_corr` −100ms、`f0_dist` −5ms、`formant_dist` −50ms）、一意に定まらない |
| 4. 1 または 2 を初期値とし、ずらし量をフィットのパラメータにする | ずれの誤差がフィット誤差に混ざる。どの指標で合わせるかが Q-005（指標の重み付け）に依存する |
| 音源の種類で定義を分ける組み合わせ（先頭が完全な0の3件は「先頭の非ゼロ標本」、オンセットのない3件は暗黙に0、など） | 音源ごとにずらし量の定義が混ざり、扱いの違いが残差に混ざりうる。全11件を所有者付与で統一し、0 も所有者が明示的に付与する |

選択肢2を採るため、Q-019「決めるために必要な観測（#113 で追加）」の合成条件の観測（選択肢3・4の判断材料）は行わない。

## スコープ外（本ADRでは決めない）

- **ずらし量の記録形式**（置き場所、フィールド名、単位、スキーマ）。所有者判断「次の作業」2 により実装側の Issue で決める
- **長さの扱い**（上記「(B)」）と、整列の実装方式（ランナで target を切り出すか、`harness/metrics.py` にずらし量を渡すか）
- **`calc_conditions` に何をどう記録するか**（使ったずらし量を記録すること自体は所有者判断「次の作業」2 に含まれる）
- **ずらし量の値。** 所有者が付与する（所有者判断「次の作業」3）
- **Q-009（区間境界の決め方、アタック20msの妥当性）。** 所有者判断「本判断に含めないこと」により、本ADRの決定範囲に含めない。Q-009 は open のまま残り、Q-009「暫定の扱い（#105 で追記）」（現行の区間別アタック指標を残差の切り分けの根拠に使わない）も本ADRでは変えない

## 結果

- `docs/06-open-questions.md` Q-019 を resolved（ADR-0012）にする
- `docs/04-metrics.md` に、指標算出の前提として時間整列の規約（(A)(B)(C)）を追記する。記録形式と長さの扱いは同文書の「未確定」に置く。`docs/04-metrics.schema.json` は変更しない（フィールドを決めていないため）
- `docs/03-preset-format.md` は変更しない（(A) により `t` の規約を変えないため）
- 区間境界 `calc_conditions.segment_boundaries_s` は、既存の定義（`docs/04-metrics.schema.json`「ノートオンを0秒とする」）を本ADRでは変えない。(A)(B) の帰結として、整列後の target ではノートオンはずらし量の位置に当たり、既存の定義のままでも区間別アタック指標の窓の起点はそこへ動く。これは Q-009 への決定の適用ではなく、Q-009（既定値 20ms の妥当性、オンセットの判定基準）も解決しない
- `docs/00-vision.md`「現在地」を、フェーズ2の着手条件（Q-019 の決定）を満たした状態に更新する。**ただし、ずらし量の付与とハーネスでの適用が済むまで、`corpus/baseline/` の指標値は時間ずれを含んだままである。** 着手条件を満たしたことは、指標が整列済みになったことを意味しない
- 実装側の Issue を起票する（記録形式と長さの扱いの決定、所有者によるずらし量の付与、ハーネスでの適用と `calc_conditions` への記録と `corpus/baseline/` の更新）
- 既存の手動プリセット `corpus/presets/spoken_hello_manual_v1.json` は、Q-019 観測2で「Harmonic 層の `partial_amplitudes` を 0.24s まで0にしており、target の時間軸に合わせている。一方 Transient 層の包絡は t=0 から鳴る」と記録されている。整列を適用すると、このプリセットのレンダと target の相対位置が変わり、指標値も変わる（観測2では、レンダ全体を遅らせると `f0_dist` が 1.12 → 11.40Hz に悪化した）。プリセットを直すかどうかは本ADRでは決めず、実装側の Issue で扱いを明示する
