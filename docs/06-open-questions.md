## Q-009. 区間境界の決め方（自動検出か注釈入力か）、およびアタック20msの妥当性
- **何が不明か**：区間別指標（`docs/04-metrics.md`）の区間境界（アタック・遷移部・定常部・
  リリース）を、オンセット検出・f0変化点検出等で自動検出すべきか、音源ごとに人手で注釈を
  付与すべきか。また、アタック区間の既定終端を0〜20msとしたことが実際のトランジェント長に対して
  妥当かどうか
- **何が決まれば進めるか**：ゴールデン音源セットへの区間注釈の付与（フェーズ1、レンダ結果を
  見てから）。自動検出の実装着手（着手するとしても本Issue #6の完了後）
- **決めるために必要な観測**：ゴールデン音源をレンダした際の区間別指標の実測値。とくに
  アタックの立ち上がり形状と、既定の20msという値の一致度合い（`corpus/manifest.json` の
  `diversity.measurements.attack_rise_ms` は音源選定用の粗い指標であり、この妥当性検証には
  流用できない点に注意）
- **暫定の扱い**：区間境界は実装に埋め込まず外部入力（設定またはマニフェストの注釈）として
  受け取る（`harness/metrics.py` の `attack_end_s` / `transition_end_s` / `sustain_end_s`）。
  アタックの既定値（0〜20ms）だけは仮の値として使う。遷移部・定常部・リリースの境界には
  既定値を置かず、注釈が与えられていない音源ではその区間を欠測として出力する
- **状態**：open

## Q-010. フォルマント推定・追跡方式の選定
- **何が不明か**：フォルマント軌跡距離（`docs/04-metrics.md` 軌跡指標）の算出に使うフォルマント推定・追跡の方式（スペクトルピーク選択 / LPC / ケプストラム包絡等）と、そのパラメータ（追跡数・フレーム長・対応付け幅）をどう決めるか
- **何が決まれば進めるか**：実在の音源（フェーズ1以降、母音・奏法変化を含む）で現在の方式の追跡誤差・破綻（フォルマントの取り違え、追跡中の欠測）が実用上問題になるかの観測
- **決めるために必要な観測**：実際のゴールデン音源の残差がどの方式・パラメータで最も素直に減るか。合成既知解（`g_formant_shift` / `h_formant_glide`）だけでは方式の優劣は決まらない
- **暫定の扱い**：`stft-peak-tracking`（STFT対数振幅スペクトルのピーク選択＋周波数近接の貪欲追跡）を既定とする。peak selection rule（振幅大→小、既選択から250Hz以上離れたものを選択）と tracking rule（前値から300Hz以内の最寄りへ継続、1ピーク1追跡）は出力JSONの算出条件に記録。LPC全極包絡のピーク選択も検討したが、合成既知解上で高次フォルマントを取りこぼし不採用。実音源での精度は未検証
- **状態**：open

## Q-011. f0推定方式の選定
- **何が不明か**：f0軌跡距離（`docs/04-metrics.md` 軌跡指標）の算出に、`librosa.pyin`（確率的YIN）以外の推定方式（単純なYIN、SWIPE、CREPE等の学習ベース手法）を採用すべきかどうか
- **何が決まれば進めるか**：実在の音源（フェーズ1以降、ゴールデン音源セットに音高が不安定な楽器・ビブラートを含む音源が増えたとき）で `pyin` の推定誤差が実用上問題になるかどうかの観測
- **決めるために必要な観測**：ビブラート・グロウル・倍音の強いノイズ成分を含む実音源に対する `pyin` の有声判定精度とf0追従誤差
- **暫定の扱い**：`harness/metrics.py` は `librosa.pyin` を既定として実装する。単純な `librosa.yin` は無声区間でも値を返してしまい「f0が存在しない入力に対してでたらめな値を返さない」という要求（Issue #8 完了条件）を満たせないため不採用。この判断はアルゴリズム選択に依存しない既知解フィクスチャ（固定f0・既知区間グライド）でのみ検証しており、実音源での精度は未検証（`docs/adr/0003-harness-runtime-and-dependencies.md` 参照）
- **状態**：open

## Q-012. レビュー単位の変更ファイル数上限（`AGENTS.md` 第5節）は生成物を除外するか
- **何が不明か**：`AGENTS.md` 第5節の「変更行数（テスト・生成物を除く）400」には生成物の除外が明記されているが、「変更ファイル数10」にはその除外が明記されていない。Issue #13 で `corpus/baseline/` に `harness.corpus_runner.run_corpus` の出力をそのまま置くと、コーパス11音源分の個別JSON + `index.json` で12ファイルになり、ワークフロー定義等と合わせると単純合計では10を超える
- **何が決まれば進めるか**：今後、生成物（`run-corpus` 等の既存ツールの出力をそのままコミットするだけのデータ）を含むPRで、ファイル数上限をどう数えるかの規約が固まる
- **決めるために必要な観測**：生成物を含むPRが実際に何度上限に抵触するか（`AGENTS.md` 第8節「3回ルール」）
- **暫定の扱い**：Issue #13 では、`corpus/baseline/` 配下のファイル（人手で内容を書いていない、既存ツールの出力をそのまま置いただけのもの）は「変更行数」の生成物除外と同じ趣旨で「変更ファイル数10」の集計対象からも除外する、という解釈を採用してPRを進める。この解釈自体が本Issueの範囲であり、レビュアが別の解釈を取るならこのQを踏まえて指摘してほしい
- **状態**：open
