## Q-009. 区間境界の決め方（自動検出か注釈入力か）、およびアタック20msの妥当性
- **何が不明か**：区間別指標（`docs/04-metrics.md`）の区間境界（アタック・遷移部・定常部・
  リリース）を、オンセット検出・f0変化点検出等で自動検出すべきか、音源ごとに人手で注釈を
  付与すべきか。また、アタック区間の既定終端を0〜20msとしたことが実際のトランジェント長に対して
  妥当かどうか
- **何が決まれば進めるか**：ゴールデン音源セットへの区間注釈の付与（フェーズ1、レンダ結果を
  見てから）。自動検出の実装着手（着手するとしても本Issue #6の完了後）
- **決めるために必要な観測**：ゴールデン音源をレンダした際の区間別指標の実測値。とくに
  アタックの立ち上がり形状と、既定の20msという値の一致度合い（`corpus/manifest.json` の
  `diversity.measurements.attack_rise_ms` は音源選定用の粗い指標であり、この妥当性検証には
  流用できない点に注意）
- **暫定の扱い**：区間境界は実装に埋め込まず外部入力（設定またはマニフェストの注釈）として
  受け取る（`harness/metrics.py` の `attack_end_s` / `transition_end_s` / `sustain_end_s`）。
  アタックの既定値（0〜20ms）だけは仮の値として使う。遷移部・定常部・リリースの境界には
  既定値を置かず、注釈が与えられていない音源ではその区間を欠測として出力する
- **観測（#105）**：ゴールデン音源11件の target を実測した。測定条件は次のとおり。`diversity.measurements.attack_rise_ms` は使っていない。測定スクリプトはスパイク（`AGENTS.md` 第3節）として破棄した
  - 共通：チャンネル平均のモノラル。振幅包絡は2.5ms窓（44.1kHzで110標本）・0.5msホップのRMS。フレーム時刻は窓の中心
  - 「最大比」は振幅包絡（上記RMS）の音源全体の最大値に対する比。標本ピーク比ではない
  - オンセット：包絡が最大比 −40dB（または −30dB）に初めて達したフレーム。以降の列の起点は −40dB のオンセット
  - 包絡最大：オンセットから探索窓（100ms / 1s）内で包絡が最大になるフレームまでの時間
  - スペクトルフラックス：オンセット−10ms（負になる場合は先頭標本）から始まるフレーム列。フレーム長5ms（44.1kHzで220標本）、ホップ2.5ms、対称Hann窓（`numpy.hanning`）、FFT長＝フレーム長（ゼロ詰めなし）。各フレームで `ln(|X|+1e-9)` をとり、直前フレームとの差の正の部分をビン平均した値をそのフレームのフラックスとする（先頭フレームは0）。定常水準は [オンセット+300ms, +800ms] に中心があるフレームのフラックス中央値
  - 整定：オンセットの −5ms〜+100ms でフラックスが最大のフレームより後で、定常水準の k 倍以下が20フレーム（50ms）連続する最初の区間の、先頭フレームの時刻
  - **フラックス整定の絶対値は実装の細部に依存する。** レビュアが細部の異なる実装（`20·log10(|X|+1e-10)` 等）で独立に再測定したところ、k=3 / 2 / 1.5 の値は音源によって大きく変わった（例：`crash_cymbal` 74.6 / 74.6 / 134.4ms、`violin_pizzicato` 3.2 / 38.2 / 222.7ms）。以下で結論に使うのは「k や探索窓で値が桁単位で変わる」という性質だけである。この性質は細部を変えた実装でも保たれた。振幅包絡の列（オンセット・窓内RMS・包絡最大）は独立再測定で一致した

  レンダ結果（`corpus/baseline/`）との照合：
  1. **既定のアタック窓 [0, 20ms) は、11件中7件でオンセットより前にある。** うち3件（`violin_pizzicato` / `violin_vibrato` / `crash_cymbal`）は target の窓内が全標本0で、baseline のアタック区間指標が3件とも完全に同じ値になっている（`msstft` 36.989、`mfcc` 1280.457、`loudness_diff_db` 248.458）。3件は同じ `provisional_v0` でレンダしており、target 側が全標本0なので値は target に依存しない。アタックについて何も測っていない。残り4件（`violin_tuning` / `tibetan_singing_bowl` / `kalimba_sample` / `spoken_hello`）も窓内は最大比 −56.5〜−72.2dB で、オンセット前の背景を測っている。P1-12 の手動プリセットでレンダした `spoken_hello` でも、アタック区間の `loudness_diff_db` は 42.433dB で、全体の 1.626dB と大きく食い違う。ただし `spoken_hello_manual_v1` はトランジェント包絡を t=0 から始めている。この食い違いには、target のオンセット（約222ms）と candidate のノートオン（0s）のずれも含まれ、両者は分離できていない（Q-019）
  2. **オンセットを起点にしても、試したどのパラメータ（包絡最大の探索窓100ms / 1s、フラックス整定の k=3 / 2 / 1.5）でも、音源ごとの代理値は20msの両側に分かれた。** 固定長1つでコーパス全体を覆えるという根拠は得られなかった（ただし代理指標そのものの妥当性は上記3のとおり未確定）。撥弦・打撃系（探索窓100msでの包絡最大まで：`violin_pizzicato` 13ms、`snare_drum_rim` 14ms、`tibetan_singing_bowl` 2.5ms、`kalimba_sample` 8.5ms）は20ms以内に収まる。一方 `crash_cymbal`（79ms）、`spoken_hello`（47.5〜155.5ms）、擦弦の `violin_vibrato` / `violin_tuning`（探索窓100msでも70ms超、1sでは890ms超）は20msを超える。`sine_440hz` / `white_noise` / `rain_light` は先頭から信号が定常的に存在し、オンセットという事象自体がない
  3. **アタック終端の代理指標は、パラメータの選び方で桁が変わる。** 振幅包絡の最大を探す窓（100ms / 1s）で `violin_pizzicato` は13ms / 295ms、`snare_drum_rim` は14ms / 708ms。フラックス整定の k で `violin_pizzicato` は 2.5 / 44.9 / 336.7ms、`violin_vibrato` は 2.5 / 2.5 / 478.9ms。この条件では、k によらず値が安定したのは `tibetan_singing_bowl` と `kalimba_sample` の2件だけだった（どの音源が安定するかも実装の細部で変わる）。オンセット自体も閾値で動く。−40dB→−30dB の移動量は `violin_tuning` 633.6ms、`spoken_hello` 23.0ms、`snare_drum_rim` 12.0ms、`violin_pizzicato` 11.5ms、`kalimba_sample` 2.5ms、`violin_vibrato` / `crash_cymbal` 1.0ms、その他0ms。20ms程度の窓に対して無視できない移動（10ms超）が4件ある
- **この観測で決まったこと・決まらなかったこと（#105）**：
  - 決まった：**ファイル先頭を起点とする既定値 0〜20ms は、このコーパスに対して妥当でない**（上記1）。区間別指標のアタック区間は、現状7/11件でオンセット前を測っている
  - 決まらなかった（resolved にしない理由）：
    1. **アタック終端の正解が観測できない。** アタック区間の目的は「トランジェント層の妥当性」（`docs/04-metrics.md`）であり、終端はターゲットのうちトランジェント成分が支配的な区間の終わりであるべきだ。しかしターゲットは層に分解されておらず、その区間を直接観測する手段がない。代理指標（振幅の立ち上がり、フラックス整定）は互いに一致せず、パラメータ次第で桁が変わる（上記3）。どのパラメータが正しいかを判定する基準もない。ここで k やピーク探索窓を選べば、固定値にせよ音源ごとの注釈基準にせよ、推測で埋めることになる（`AGENTS.md` 第6節・第7節）
    2. **オンセットの判定基準も決まらない。** −40dB と −30dB の間だけでも10ms超の移動が4件ある（上記3）。どの閾値が正しいかを判定する基準がない
    3. **target のオンセットと candidate のノートオンの時間整列が未定義である。** 区間別指標は target と candidate を同じ絶対時刻で切り出す（`harness/metrics.py` の `_segment_slice_bounds`）。一方プリセットの時間軸はノートオンを0とする（`docs/03-preset-format.md`）。オンセットを起点にアタック窓を置いても、candidate 側のアタックがその窓に来る保証はない。これはアタック窓の定義だけでは閉じないため Q-019 に分けた
    4. **付与方法（人手か自動検出か）は、1と2の判定基準に依存する。** 自動検出はそのパラメータの正当化を要し、エージェントによる人手付与も数値の基準なしにはできない（`AGENTS.md` 第1節）。所有者が聴いて付与する案は、注釈を「音質判断」ではなく「指標の入力となる前提データ」とみなして第1節と整合させられるか、という所有者判断を含むため、エージェントは決めない
- **決めるために必要な観測（#105 で追加）**：(a) トランジェント成分が支配的な区間の長さを観測する手段。ターゲット側で直接観測する手段は現状ない。間接的な手段としては、フェーズ2でフィット済みプリセットが揃えば、音源ごとに Transient 層をオン/オフしてレンダし、残差がどの時間範囲で変わるかを観測できる。ただしこれはモデル側（フィットされた `transient.duration`）の広がりを見るもので、フィット誤差や能力ギャップの混入を切り分ける必要がある。(b) または、観測に代えてアタック終端とオンセットの**定義**を所有者が仕様として決める。その場合もパラメータの選択根拠は別途要る
- **暫定の扱い（#105 で追記）**：既定値 0〜20ms は実装上そのまま残す（`harness/metrics.py` の `DEFAULT_ATTACK_END_S`。変更は `corpus/baseline/` を動かすため #58・#96 の範囲）。ただし上記1のとおり、**現行の区間別アタック指標を残差の切り分け（`docs/01-architecture.md`）の根拠に使ってはならない**。7/11件でアタックを測っていない
- **状態**：open（#105 の実測で、ファイル先頭起点の既定値 0〜20ms が妥当でないことは確認した。アタック終端とオンセットの判定基準は観測できておらず、付与方法も決まらないため resolved にしない。target と candidate の時間整列は Q-019 に分けた。#58 の注釈付与はこれらを待つ）

## Q-010. フォルマント推定・追跡方式の選定
- **何が不明か**：フォルマント軌跡距離（`docs/04-metrics.md` 軌跡指標）の算出に使うフォルマント推定・追跡の方式（スペクトルピーク選択 / LPC / ケプストラム包絡等）と、そのパラメータ（追跡数・フレーム長・対応付け幅）をどう決めるか
- **何が決まれば進めるか**：実在の音源（フェーズ1以降、母音・奏法変化を含む）で現在の方式の追跡誤差・破綻（フォルマントの取り違え、追跡中の欠測）が実用上問題になるかの観測
- **決めるために必要な観測**：実際のゴールデン音源の残差がどの方式・パラメータで最も素直に減るか。合成既知解（`g_formant_shift` / `h_formant_glide`）だけでは方式の優劣は決まらない
- **暫定の扱い**：`stft-peak-tracking`（STFT対数振幅スペクトルのピーク選択＋周波数近接の貪欲追跡）を既定とする。peak selection rule（振幅大→小、既選択から250Hz以上離れたものを選択）と tracking rule（前値から300Hz以内の最寄りへ継続、1ピーク1追跡）は出力JSONの算出条件に記録。LPC全極包絡のピーク選択も検討したが、合成既知解上で高次フォルマントを取りこぼし不採用。実音源での精度は未検証
- **状態**：open

## Q-011. f0推定方式の選定
- **何が不明か**：f0軌跡距離（`docs/04-metrics.md` 軌跡指標）の算出に、`librosa.pyin`（確率的YIN）以外の推定方式（単純なYIN、SWIPE、CREPE等の学習ベース手法）を採用すべきかどうか
- **何が決まれば進めるか**：実在の音源（フェーズ1以降、ゴールデン音源セットに音高が不安定な楽器・ビブラートを含む音源が増えたとき）で `pyin` の推定誤差が実用上問題になるかどうかの観測
- **決めるために必要な観測**：ビブラート・グロウル・倍音の強いノイズ成分を含む実音源に対する `pyin` の有声判定精度とf0追従誤差
- **暫定の扱い**：`harness/metrics.py` は `librosa.pyin` を既定として実装する。単純な `librosa.yin` は無声区間でも値を返してしまい「f0が存在しない入力に対してでたらめな値を返さない」という要求（Issue #8 完了条件）を満たせないため不採用。この判断はアルゴリズム選択に依存しない既知解フィクスチャ（固定f0・既知区間グライド）でのみ検証しており、実音源での精度は未検証（`docs/adr/0003-harness-runtime-and-dependencies.md` 参照）

## Q-017. Formant filter bank の構成（並列バンク vs 直列カスケード）と決定論の保証範囲
- **何が不明か**：`docs/02-engine-spec.md` 層[3]「Formant filter bank」は、4バンドが「並列（各バンドの出力を加算）」か「直列（カスケード）」かを明示していない。また `docs/adr/0006` の決定論方針（スカラーループで自動ベクトル化・FMA依存を避ける）が「同一バイナリ内の再実行のみ保証」か「コンパイラをまたいでビット一致まで保証する」かの範囲が明示されていない
- **何が決まれば進めるか**：
  1. バンドの接続方式。これは音響的な挙動（各バンドの `gain` の独立性、`gain:0` の切断の意味）を変える。並列なら各バンドが独立に効き `gain` も独立。直列（共振器の連鎖）は古典的なフォルマント合成に近く、あるバンドの `gain` を0にすると全体を通滅する
  2. 決定論の保証範囲。コンパイラの既定最適化（MSVC/Clang の `-O2`、GCC の FMA 縮約）や `std::tan` の libm 実装差が、再帰フィルタの丸め誤差を時間方向に蓄積させるため、**コンパイラをまたいだビット一致は現実的に成立しない**
- **決めるために必要な観測**：ループ2でコーパス残差を見て、並列と直列のどちらが残差を素直に減らすか。決定論の範囲は `docs/adr/0006`・`docs/adr/0008` の適用方針（同一コミットに対する同一環境での再実行の決定性を CI のリグレッションテストで担保する）で周知一致
- **暫定の扱い（P1-10 #55）**：
  1. **並列バンクを採用**：各バンドは TPT 状態変数バンドパスを1個持ち、全バンドの出力を加算する。各バンドの `freq` / `Q` / `gain` が独立に効くことをテストで保証する（Issue #55 完了条件）。直列カスケードとの差はループ2で観測してから改定
  2. **決定論は「同一ビルド・同一環境での再実行」を保証し、コンパイラをまたいだビット一致は保証しない**。`test_formant` の bit-identical テストで担保する。実装はスカラーループで書き、積極的最適化フラグは追加しない（`docs/adr/0006` を踏襲）。コンパイラまたいだビット一致が必要になった場合は ADR を改定して決める
- **状態**：open

- **何が決まれば進めるか**：ループ2でコーパス残差を見て、加算方式に対する実際の要求（レベルの相対変化のみで十分か、f0 への乗算型変調が必要か）が判明する。`curve` の exp/step/spline が何を意味するかも、需要が出た時点で決める
- **暫定の扱い（P1-11 #56）**：所有者の承認により**加算方式**を採った。`dest(t) = base(t) + mod(t)`、ただし `mod(t) = source(t) × route.depth`。
  1. **LFO**：波形を `2π·rate·t` の位相で [-1,1] に正規化し、LFO 自身の `depth` を乗算（source 値の一部）。`sync` はヘッドレス v0 ではノートオンが常に 0.0 から始まり tempo/clock が存在しないため位相に影響しない。波形は v0.1 では `sine` / `triangle` / `square` / `saw` をサポートし、未知の波形は PresetError
  2. **Envelope**：ブレークポイント列を linear 補間し、範囲外は定数外挿
  3. **curve**：v0.1 では `linear` のみ対応。exp/step/spline は適用式が未定義のため PresetError で停止する（黙って線形近似しない）
  4. **destination の単位**：変調量は目的地の値域に加算される。`freq`/`f0`/`q` はそのまま Hz / 無次元、`*_db`（transient.gain / formant gain / spectral_envelope）は dB 値に加算してから振幅へ変換
  5. **transient.duration は時間変調の対象外**：レンダ長そのものを決めるパラメータに時間変調を掛けると「各サンプルの長さ」が不定になり正当な適用が定義できないため PresetError で弾く（routing の「パス存在」検証とは別の意味検証、`validateModulatableDestinations`）
  6. **無効な層へのルート**：変調先の層が `enabled: false` のとき、その層は出力に寄与しない（既存の層ゲート）ため、変調しても音には現れない。これは「無効層を変調が有効化しない」という仕様の明示であり、テストで検証する
- **状態**：open（フェーズ2の観測で確定・変更する）

## Q-019. target のオンセットと candidate のノートオンの時間整列
- **何が不明か**：ゴールデン音源の target には、オンセットより前に、無音または最大比 −40dB 未満の信号だけが続く長い区間を持つものがある（#105 の実測で、−40dB オンセットが `violin_pizzicato` 727.6ms、`violin_vibrato` 1119.2ms、`crash_cymbal` 404.3ms、`kalimba_sample` 1385.1ms、`spoken_hello` 221.8ms など。Q-009 の観測表）。一方プリセットの時間軸はノートオンを0とし（`docs/03-preset-format.md`）、指標は target と candidate を同じ絶対時刻で比較する（`harness/metrics.py`。全体指標・区間別指標・軌跡指標のいずれも）。target のオンセットと candidate のノートオンを揃える責任をどこが持つかが決まっていない。候補は (1) プリセットが先頭の無音も時系列で表現する、(2) レンダラまたはランナが candidate をオンセット分遅らせる、(3) 指標側が target をオンセット分ずらして比較する、の3つ。(3) を採る場合も、target ファイル自体は取得したまま変更しない（`corpus/manifest.json` の `note_en`。sha256 で検証しており、音源セットの変更には ADR が要る：`docs/adr/0004-golden-corpus.md`）
- **何が決まれば進めるか**：Q-009 のアタック窓の起点（オンセット）を区間別指標で使えるようになること。フェーズ2のフィッティングで、先頭無音のずれを残差として扱うかどうか
- **決めるために必要な観測**：(1) の場合、現行のプリセット形式・エンジン（`docs/02` `docs/03`）で先頭の無音を表現できるか（全層を t<オンセット で実質無音にできるか。たとえば Transient 層の開始位置を遅らせるパラメータはなく、スペクトル包絡の dB 値を下げることで代替できるかは未確認）。(2)(3) の場合、オンセットの判定基準（Q-009 で未確定）
- **暫定の扱い**：現行どおり target と candidate を同じ絶対時刻で比較する。オンセットが遅い音源では、全体指標・区間別指標・軌跡指標のいずれにも時間ずれによる誤差が含まれうる（#105 で `spoken_hello` のアタック区間 `loudness_diff_db` 42.433dB と全体 1.626dB の食い違いとして観測。ずれと音色差の寄与は未分離）
- **観測（#113）**：決定のための観測を行った。フェーズ2の着手条件である（#45 の所有者決定）。測定条件は次のとおり。測定スクリプトはスパイク（`AGENTS.md` 第3節）として破棄した
  - 環境：Windows / MSVC でこの時点の main のエンジンをビルドし、`harness/metrics.py` の関数を変更せずに呼んだ。`spoken_hello_manual_v1` を target のサンプルレート（48kHz）でレンダした指標は、`corpus/baseline/spoken_hello.json` と小数第4位まで一致した
  - 「オンセット」は Q-009 の観測表と同じ定義（2.5ms窓のRMS包絡が最大比 −40dB に初めて達したフレームの中心時刻）。以下の結論は、この定義が正しいことを前提にしていない。ずらし量の例として使っただけである
  - 「純粋なずれ」：candidate を **target 自身を d だけずらした信号**にした（長さは target と同じ。遅らせる場合は先頭を0で埋めて末尾を捨てる）。音色差はゼロなので、指標値はずれだけによる
  1. **候補 (1)「プリセットが先頭の無音を表現する」は、近似としては表現できる。** `spoken_hello_manual_v1` の全時系列の `t` をオンセット（221.75ms）だけ後ろにずらし、`partial_amplitudes` はオンセット直前まで0の点を、`spectral_envelope` は低い dB 値の点を先頭に足し、`transient.duration` を同じだけ延ばしてレンダした
     - オンセット前の出力は、Harmonic 層は振幅0の点で厳密に0になる。Transient 層は開始位置を遅らせるパラメータがないため、包絡の dB 値を下げるしかない。−120dB を置くとオンセット前の最大振幅は元のレンダのピーク比 −117.3dB、−7000dB を置くと厳密に0になった。後者は `pow(10, dB/20)` のアンダーフローによるもので、仕様上の意味はない。点を足さないと、オンセット前に Transient 層がピーク比 −5.7dB で鳴る

     - ただし**指標上の差は小さかった**。target に対する指標を「ずらしたプリセットのレンダ」と「元のレンダをランナ側で遅らせたもの」で比べると、全体 `msstft` 8.062 / 8.080、`mfcc` 189.9 / 189.1、`loudness_diff_db` 0.560 / 0.636、`transient_env_corr` −0.228 / −0.205、`f0_dist` 11.30 / 11.40Hz だった。例外は `formant_dist` の 822.9 / 708.6Hz である。この指標は不安定である。下記4の条件（オンセット前だけが0で、オンセット以降は target と同一の信号）でも、`tibetan_singing_bowl` 679.9Hz（違うのは先頭91ms、ファイルの0.38%）、`violin_vibrato` 151.6Hz になった。追跡が最初にピークの見つかったフレームで初期化され、以降は近い値へ貪欲に継続するため（`harness/metrics.py` の `estimate_formant_tracks`）、先頭の違いが軌跡全体に波及する。なお両者の `loudness_diff_db` が元のレンダ（1.626dB）より小さいのは、candidate が 41600 → 52244 標本に延び、全長の RMS が薄まるためである（`harness/metrics.py` の `loudness_diff_db` は長さを揃えない。1.626 − 10·log10(52244/41600) = 0.636）。**この1例では、表現できるかどうかでも指標値でも (1) と (2) を区別できなかった**
  2. **既存の手動プリセットは、層ごとに時間軸の置き方が違う。** `spoken_hello_manual_v1`（P1-12）は、Harmonic 層の `partial_amplitudes` を 0.24s まで0にしており、target の時間軸に合わせている。一方 Transient 層の包絡は t=0 から鳴る。#105 が観測した「アタック区間 [0, 20ms) の `loudness_diff_db` 42.433dB」は、この Transient 層が target の背景（最大比 −56.5dB）の上で鳴っていることによる。レンダ全体をオンセット分遅らせると Harmonic 層がずれて `f0_dist` が 1.12 → 11.40Hz に悪化し、Transient 層だけをプリセット内で遅らせると、`transient_env_corr` 0.666 → 0.794、全体 `mfcc` 255.9 → 158.8 は改善し、全体 `msstft` 7.554 → 7.885、`bands` の全5帯域（0〜200Hz 6.14 → 8.61、200〜800Hz 11.28 → 12.40、800〜2000Hz 7.16 → 7.27、2000〜5000Hz 7.25 → 7.44、5000〜20000Hz 7.38 → 7.73）、`f0_dist` 1.124 → 1.160Hz、`formant_dist` 848 → 855Hz は悪化した。全体 `loudness_diff_db` は 1.626 → 1.585dB だった。**整列の規約が決まっていないため、手書きのプリセット1つの中でも規約が混在している**

- **この観測で決まったこと・決まらなかったこと（#113）**：Q-019 は、次の3つに分けられる。(A) 整列をプリセットが持つかハーネスが持つか。(B) ハーネスが持つ場合、target のオンセット前の区間を比較に含めるか。(C) ずらし量（target のファイル内で candidate のノートオンに当たる時刻）をどう得るか。**(C) が決まらないため resolved にしない。** ADR-0012 は (C) の決定と合わせて書く
  - (A) **既存の文書から結論を導ける。観測はそれに反しない。整列はハーネスが持ち、プリセットの `t` はノートオンを0とする規約（`docs/03`）のまま変えない**。主な根拠は文書である。(1) ではフィット済みプリセットに録音ごとの先頭無音（−40dB オンセットで `spoken_hello` 約0.22s、`kalimba_sample` 約1.39s）が入り、DAW でノートオンしてもその時間だけ鳴らない。これは「DAW上で演奏・調整・オートメーションできる形で手渡す」（`docs/00-vision.md`）に反する。観測は補助にとどまる。上記1では (1) と (2) の指標値の差は小さかったが、1音源・1プリセットの観測であり、(1) を退ける根拠ではない。「(1) を採っても指標上は得るものがなかった」という事例である。上記2（層ごとに時間軸が混在している）は、どちらかに規約を決める必要があることの根拠であり、ハーネス側を選ぶ根拠ではない。ずらし量はプリセットの外に置くことになる。どこに置くか（マニフェストの注釈か、評価時の探索結果か、フィットの記録か）は (C) の選択肢によって決まる。**所有者の確認を要する**
  - (B) **観測から結論を出せる。target のオンセット前は比較から外す**（候補 (3) の扱い）。根拠は上記4。(A) の規約（ノートオン前に音を出さない）の下で0を埋めて比較に含めると、どう追い込んでも下がらない残差が入る。現行コーパスの全体 `msstft` では、この残差は `spoken_hello` 以外で小さい（0.25以下。`mfcc` は `kalimba_sample` 1.4）。それでも、切り分けを誤らせる残差を構造上なくせる方を採る。代償は3つある。ずらし量が実際より遅く見積もられると、その区間の target の音が評価されなくなる。早く見積もられると、背景の一部が比較に戻り、上記4と同じ残差が入る。target を切り出すと長さが変わり、`loudness_diff_db` が長さの比だけで動く（上記1・3）。したがって (B) の安全性は (C) の精度に依存し、長さの扱いは実装で決める必要がある（Q-014 のレンダ長とも関係する）。実装上ランナで target を切り出すか `harness/metrics.py` にずらし量を渡すかは、実装Issueで決める。**所有者の確認を要する**
  - (C) **決まらない。** 必要な入力はずらし量という1つのスカラーだけである。ただしその値を、判定基準のない代理指標から選ぶことになる。これは Q-009 の「決まらなかった」2（オンセットの判定基準）と同じ問題である。−40dB と −30dB だけでも 4/11 件で 10ms 超、`violin_tuning` では 633.6ms 動く。上記3のとおり、音色差ゼロの条件では、`spoken_hello` の閾値差 23ms だけで全体 `msstft` 0.93・`mfcc` 40.0 のずれが生じる。`violin_tuning` の閾値差 633.6ms では全体 `msstft` 1.52・`mfcc` 56.1 で、+100ms のずれ（1.08・27.2）より大きい。先頭が完全な0の3件（`violin_pizzicato` / `violin_vibrato` / `crash_cymbal`）では、「先頭の非ゼロ標本」（722.7 / 1114.6 / 400.5ms）という閾値を使わない定義が取れる。ただしそれが candidate のノートオンに当たる時刻として正しいかは別問題である。−40dB オンセットとの差は 3.8〜4.9ms、`violin_pizzicato` の −30dB オンセットとはさらに 11.5ms 離れている。残る8件は先頭の標本から非ゼロで、この定義が取れない。そのうち `sine_440hz` / `white_noise` / `rain_light` は、オンセットという事象自体がない（Q-009 観測の2）。**所有者判断が要る選択肢と帰結**は次のとおり
    1. **閾値検出を操作的な定義として採る**（例：Q-009 の −40dB）。自動で再現できる。閾値を選ぶ根拠は観測されておらず、Q-009 の「決まらなかった」2 は解消しない。`violin_tuning` など閾値差の大きい音源では、整列が閾値の選び方で数百ms変わることを受け入れることになる
    2. **所有者が聴いて音源ごとにずらし量を付与し、マニフェストに前提データとして記録する**。11件なら作業量は小さい。Q-009 の「決まらなかった」4 と同じく、聴いて付けた値を「音質判断」ではなく「指標の入力となる前提データ」とみなして `AGENTS.md` 第1節と整合させられるか、という所有者判断を含む
    3. **評価のたびに、指標を最小にするずらし量を探す**。閾値は要らない。ただし上記5のとおり、音色差があると最良のずらし量が指標ごとに割れる。指標をタイミングのずれに対して盲目にし、探索範囲とどの指標を使うかという新しいパラメータを持ち込む
    4. **1 または 2 の値を初期値とし、ずらし量をフィットのパラメータとしてプリセットの外に記録する**。フィットでずれを補正できる。一方で、ずれの誤差がフィット誤差に混ざり、どの指標で合わせるかは 3 と同じく Q-005 に依存する
    - 音源の種類で分ける組み合わせもありうる。たとえば先頭が完全な0の3件だけは「先頭の非ゼロ標本」を使い、残りは 1〜4 のいずれかで扱う。オンセットのない3件（`sine_440hz` / `white_noise` / `rain_light`）は、ずらし量0とする扱いが自然だが、これも決定が要る。帰結として、音源ごとにずらし量の定義が混ざり、コーパス単位で残差を比べるときに、扱いの違いが残差に混ざりうる
- **決めるために必要な観測（#113 で追加）**：選択肢 1・2 の値の正しさを判定する基準は、Q-009 と同じく観測できない。選択肢 3・4 が使えるかどうかは、一部なら今すぐ観測できる。答えの分かった合成条件を作ればよい。target を既知の d だけずらし、音色差を段階的に加える（帯域ゲインの変更や雑音の付加など）。そのうえで、格子探索で d を復元できるか、どの程度の音色差から最良のずらし量が指標間で割れ始めるかを見る。ただし、合成した音色差が実際のフィット残差を代表するかは、この観測では分からない。実際の残差での評価にはフィット済みプリセットが要り、フェーズ2を前提とする（Q-009 の観測 (a) と同じ循環）
- **何が決まれば進めるか（#113 で追記）**：(C) の選択肢のどれを採るかの所有者判断と、(A)(B) の結論の確認。これが揃えば ADR-0012 を書いて Q-019 を resolved にし、実装Issueを起票する。実装Issueの範囲は、ずらし量の置き場所と取得、ハーネスでの適用と長さの扱い、`calc_conditions` への記録、`corpus/baseline/` の更新。**フェーズ2の着手を止めているのはこの (C) である**
- **決定（#120 ADR-0012）**：所有者判断（[#120 のコメント](https://github.com/ycums/llm-luthier-vst/issues/120#issuecomment-5651990118)）を受けて決定した。詳細・採用しなかった案とその理由は `docs/adr/0012-target-candidate-time-alignment.md` 参照
  - (A) 整列はハーネスが持つ。プリセットの `t` はノートオンを0とする規約（`docs/03`）のまま変えない
  - (B) target のずらし量より前は比較から外す。長さの扱い（`loudness_diff_db` が長さの比で動く点、Q-014 との関係）は実装側の Issue で決める
  - (C) 選択肢2を採る。所有者が聴いて全11件にずらし量を付与し、前提データとして記録する。オンセットのない `sine_440hz` / `white_noise` / `rain_light` にも所有者が明示的に 0 を付与し、先頭が完全な0の3件にも別定義を使わない。`AGENTS.md` 第1節との関係（エージェントの判断に対する制約であり、所有者が付与する時刻のラベルは音質の判断ではなく前提データ）は ADR-0012 に記載した。選択肢2を採るため、上記「決めるために必要な観測（#113 で追加）」の合成条件の観測は行わない
  - 本決定は Q-009 に適用しない（所有者判断「本判断に含めないこと」）。Q-009 は open のまま
- **決定後に残っている作業**：ずらし量の記録形式と長さの扱いの決定（#124）→ 所有者によるずらし量の付与（#125）→ ハーネスでの適用・`calc_conditions` への記録・`corpus/baseline/` の更新（#126）。**これらが済むまで、上記「暫定の扱い」のとおり指標値は target と candidate を同じ絶対時刻で比較した値であり、時間ずれによる誤差を含む**
- **状態**：resolved（ADR-0012）

## Q-020. 同じ Linux レンダWAVを入力にしても、Windows で算出した指標値が baseline と相対4e-4程度ずれる
- **何が不明か**：`docs/adr/0008`「8.」(a)・「将来への注記」に記録されている観測で、CIの成功run（[34054474598](https://github.com/ycums/llm-luthier-vst/actions/runs/34054474598)）のLinuxレンダWAVを固定入力とし、OS だけを Windows に変えて `overall.msstft` を算出すると、baseline（Linux算出値）と相対 4e-4 程度ずれる。同ADRの許容誤差（`rel_tol=1e-12`）や、最終桁の丸め誤差（ローカル観測で最大 ~4.0e-15）では説明できない大きさである。原因（依存パッケージのバージョン差、FFTバックエンドの違い、リサンプリング経路の違いなど）は調査されていない
- **何が決まれば進めるか**：原因の切り分け観測が行われ、Windows上でも baseline の生成・比較が可能になるか、あるいは「Windowsでは行わない」ことが恒久方針として明文化されるか
- **決めるために必要な観測**：依存パッケージ（NumPy・librosa・scipy等）のOS別ビルドのバージョン一致確認、FFTバックエンド（pocketfft等）の実装差の切り分け、リサンプリング経路（音源読み込み時のサンプルレート変換の有無）の差の切り分け。いずれも Linux と Windows の両方で同一入力WAVに対する中間値を比較する必要がある
- **暫定の扱い**：Windows では baseline を生成・検証しない。`docs/04-metrics.md` の baseline 更新手順（`run-corpus` を実行して `corpus/baseline/` をコミットする）は、Linux 環境での実行を暗黙の前提とする（`docs/adr/0008`「8.」将来への注記）
- **状態**：open

## Q-021. エンジンCLI（`luthier-render`）の標準出力・標準エラー出力のエンコーディングがUTF-8であることを仕様（`docs/02` `docs/03`）に明記していない
- **何が不明か**：`engine/CMakeLists.txt` の `/utf-8`（MSVC）により、エンジンは文字列リテラルをUTF-8で保持し、`engine/cli/src/main.cpp` は日本語エラーメッセージ（「エラー: 」「予期しないエラー: 」等）をそのままUTF-8で `std::cerr` に書く（PR #64 / S-002 で導入）。Issue #122 の修正（`harness/corpus_runner.py::_render` 等で `subprocess.run` に `encoding="utf-8"` を明示する）は、この「エンジンCLIの標準出力・標準エラー出力は常にUTF-8」という前提が正しいことに依存する。しかし `docs/02-engine-spec.md` `docs/03-preset-format.md` のいずれにも、CLIの出力エンコーディングを定めた記述がない。したがって、この前提が「決まった仕様」なのか「たまたま現在のビルド設定がそうなっている実装の詳細」なのかが文書上は不明である
- **何が決まれば進めるか**：エンジンCLIの標準出力・標準エラー出力のエンコーディングを仕様として固定する（今後のエンジン実装・ビルド設定変更がこれを破ってはならない制約にする）かどうかの所有者判断
- **決めるために必要な観測**：不要（`/utf-8` フラグと `main.cpp` の実装を読めば現状の挙動は確定できる。必要なのは所有者判断であり、追加の実測は要らない）
- **暫定の扱い**：Issue #122 の実装PRでは、この前提を「現状のエンジン実装の事実」として扱い、`harness/corpus_runner.py` と `tests/test_engine_cli_wav_compat.py` の読み手側に `encoding="utf-8"` を明示した（対応する仕様PR・ADRは書いていない。実装のみのPRで仕様変更を含めない、`AGENTS.md` 第5節）。エンジン側の出力エンコーディングを変える変更が入ると、この前提が無言で壊れる
- **状態**：open
